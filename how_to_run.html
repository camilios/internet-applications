دليل عملي لهذا المشروع: أوامر Bash واضحة، تشغيل ثلاث مرات، أين تجد الأدلة، كيف تشرح قبل وبعد، وما تفعله عند الفشل. نفذ المسار الأساسي أولًا،ثم انتقل للخيارات إذا طلبها الأستاذ.

01

المسار الأساسي الذي تنفذه أمام الأستاذ

ابدأ بـ dashboard: ثلاث تشغيلات، وملفات جديدة، ومقارنة مع الأرشيف.

استعمل Ubuntu داخل WSL لأن Docker في هذا المشروع يعمل هناك. احتفظ بنافذة Ubuntu مفتوحة طوال العرض. مشغّل المقابلة يستخدم صور المشروع الموجودة، ويسجل الدخول لقراءة dashboard؛ لذلك ليس بلا كتابة مطلقًا: قد تتجدد مفاتيح الكاش وعدادات الدخول أو الرموز، لكنه لا يعيد seed ولا يمسح جداول الأعمال.

1 ـ افتح Ubuntu من PowerShell

PowerShell فقط
wsl.exe -d Ubuntu

بعد الدخول تصبح الأوامر التالية أوامر Bash في Ubuntu، فلا تلصقها مباشرة في PowerShell.

2 ـ انتقل إلى المشروع

Ubuntu / Bash
cd /mnt/e/projects/internet-applications

هذا هو مسار WSL المستعمل في ملفات المشروع؛ إذا نقلت المشروع غيّر المسار إلى مكانه الفعلي.

3 ـ افحص البيئة الموجودة

Ubuntu / Bash — فحوص استعداد
docker info
docker compose version
command -v python3
docker image inspect grafana/k6:latest
test -f perf/interview_run.sh

يجب أن يستجيب Docker، وأن تظهر Python3، وأن تكون صورة k6 والملفات موجودة. لا تحتاج تثبيت k6 على Windows لهذا المسار.

4 ـ شغّل الخدمات الخلفية الموجودة

Ubuntu / Bash — صور موجودة دون build
docker compose up -d --no-build --wait mysql mysql-replica inventory-mysql redis inventory-service backend scheduler
docker compose --profile performance up -d --no-build --wait loadtest-proxy
docker compose --profile performance ps

شغّل هذه الخطوة عند الحاجة قبل العرض. mysql-replica هنا هي النسخة المهيأة سابقًا؛ تشغيل حاويتها لا يهيئ replication من الصفر. الأمر لا يشغّل frontend. بدء backend قد ينفذ منطق startup والمهاجرات المعلقة وفق صورته.

5 ـ تحقق من استجابة backend ومن صورة k6

Ubuntu / Bash
curl -fsS http://localhost:8000/up
docker run --rm grafana/k6:latest version

نجاح/up يثبت الصحة الأساسية، وليس صحة كل gRPC أو المصادقة أو مخطط البيانات. الإصدار المحفوظ مع النتائج السابقة v2.3.0؛ سجل أي اختلاف بدل تجاهله.

6 ـ افتح ملف السيناريو واشرح الحمل

اعرض dashboard.js ثم common.js. وضح:5 ثوانٍ صعود إلى 5VUs، ثم 20 ثانية ثبات، ثم 5 ثوانٍ نزول، وثانية تفكير لكل دورة. setup للدخول و GET للعملية و Trend خاصة بزمنها.

8 ـ افتح مجلد النتائج الذي طُبع

سيطبع مسارًا تحت docs/performance/interview/ بصيغة تاريخ-وقت-PID/dashboard. افتح هذا المسار من VSCode، ثم comparison.txt ثم JSON و log. لا تعوّضه بمجلد قديم وتصفه بأنه ناتج جلسة العرض.

أقول للأستاذ: «سأقيس النسخة المنشورة الحالية ثلاث مرات بنفس الحمل. قبل التحسين لدي baseline تاريخية محفوظة؛ المشغّل لا يعيد النسخة القديمة الآن. سأعرض النتائج والأخطاء ومنهج التجميع قبل أن أقول إن هناك تحسنًا.»
02

ماذا يفعل الأمر الأساسي بالضبط؟

اعرف ما ينفذه المشغّل حتى تستطيع تفسير كل ملف.

  1. يتحقق من اسم السيناريو؛ يسمح بأربع عمليات فقط، والافتراضي dashboard.
  2. يهيئ proxy الموجود ضمن profile الأداء ويتحقق من صورة k6 والشبكة.
  3. ينشئ مجلدًا مؤرخًا جديدًا داخل interview، ويسجل إصدار k6 وأعداد الجداول.
  4. يشغّل k6 ثلاث مرات، مع RUN_ID مختلف لكل تشغيل، ونسخة سيناريوهات مركبة للقراءة فقط.
  5. يحفظ JSON مجمعة و log لكل تشغيل، ثم يستدعي interview_compare لإظهار المقارنة.

تشغيل بقية السيناريوهات

كل أمر من الأوامر التالية ينفذ ثلاث تشغيلات لعملية واحدة.

الأوامر مستقلة. تنفيذها كلها متتالية يعطي 12 تشغيلًا؛ اسم المجلد الجديد يطبع لكل مجموعة.

السيناريوالمسارما أشرحه؟
products-list/api/products?page=N&category_id=Nصفحات 1–20 وتصنيفات 1–5؛ مع 15 منتجًا قد تكون قراءات كثيرة فارغة.

افتح حقول JSON بهذا الترتيب

  1. endpoint_errors.value و http_req_failed.value و checks.fails: تشخيص الأخطاء أولًا.
  2. endpoint_duration ثم p(50) و p(95) و p(99): زمن العملية بالميلي ثانية.
  3. http_reqs.count و rate: العدد والمعدل ويشملان login عند وجوده.
  4. conditional_hits.count:304 مقبولة في common،وتؤثر على نقل الجسم.
  5. data_received.count: مجموع البايتات للتشغيل، وليس حجم JSON واحدة.

05

عرض قبل وبعد بصدق أمام الأستاذ

هناك أرشيف قبل التحسين، وأرشيف بعد، وتشغيل حالي؛لا تخلطها.

  1. افتح BEFORE_AFTER.md لعرض جدول 10 نوفمبر ومنهجه.
  2. افتح before-after.json عند baseline_rerun=false ومصدري المقارنة.
  3. لإثبات before افتح 3 ملفات من baseline/.
  4. لإثبات after المحفوظة افتح RESULTS.md ثم 3 ملفات العملية في ذلك المجلد.
  5. لإثبات التشغيل أمام الأستاذ افتح مجلد interview الذي أنشأته الآن،وليس أرشيف after فقط.

06

إذا طلب الأستاذ CSV أو فحص gzip

خطوات اختيارية بعد تجهيز الخدمات و proxy في المسار الأساسي.

CSV للنسخة الحالية

مشغّل المقابلة الأساسي ينتج JSON و log، ولا ينتج CSV. إذا طُلبت عينات CSV، نفذ الكتلة التالية كاملة من جذر المشروع في Ubuntu. ستجري تشغيلًا إضافيًا واحدًا باسم current-dashboard، لا baseline تاريخية.

Ubuntu / Bash — تشغيل واحد اختياري مع CSV وملخص JSON
csv_dir="docs/performance/interview/manual-csv-$(date +%Y%m%d-%H%M%S)-$$"
mkdir -p "$csv_dir"
run_id=$(( $(date +%s) % 200 + 1 ))
docker run --rm --network internet-applications_ecommerce-network --user 0 \
  --volume "$PWD/perf/k6:/scripts:ro" \
  --volume "$PWD/$csv_dir:/evidence" \
  --env "RUN_ID=$run_id" \
  grafana/k6:latest run --no-thresholds \
  --out csv=/evidence/current-dashboard.csv \
  --summary-export /evidence/current-dashboard.json \
  /scripts/dashboard.js
printf 'Saved to: %s\n' "$csv_dir"

كل سطر يستكمل سابقه في Bash؛ احتفظ بعلامة\ في نهاية أسطر Docker. المجلد جديد باسم وتوقيت مختلفين لتفادي الكتابة فوق الأرشيف.

CSV تحتوي نقاط مقاييس بأسماء وأوقات وقيم؛ الطلب الواحد يولد عدة مقاييس، لذلك السطر ليس بالضرورة طلبًا كاملًا. JSON هنا ملخص. هذا التشغيل المنفرد لا يحقق شرط ثلاث تشغيلات ولا أسماء ملفات interview_compare؛ فلا تمرر مجلده للمقارن كما هو بدون التجهيز المناسب. المسار الأساسي هو الأسهل للمقارنة المكونة من ثلاث تكرارات. مرجع CSV الرسمي.

قياس gzip الحالي

نفذ السيناريو المتخصص إذا كان السؤال عن ضغط جسم الرد وصحته بعد الفك. لا يرسل If-None-Match، ويشترط 200 ومصفوفة data غير فارغة لا تتجاوز 15 ونوع price سلسلة.

صورة k6 أو backend مفقودةالمسار يفترض صورًا موجودة. جهّز الصور والإصدار المقصود قبل المقابلة وسجلنسخها؛ سحب latest عشوائيًا قد يغير إصدار k6 ويؤثر على قابلية مقارنة المخرجات.
No such file أو مسار المشروع خطأتأكد من cd داخل Ubuntu وأن perf/interview_run.sh موجودة. PowerShell يستعمل E:/ بينما Bash يستعمل/mnt/e/.
bad interpreter أو$\rملف Bash محفوظ بنهايات CRLF. افتحه في المحرر واضبط End of Line إلى LF ثم احفظه. لا تغيّر منطق الاختبار أو محتواه أثناء تصحيح الترميز.
الشبكة غير موجودة أو DNS للـ proxy يفشلنفذ خطوة Compose المطلوبة وتحقق من project/network الفعليين؛ المشغّل مرتبط باسم internet-applications_ecommerce-network. إعداد المشروع المختلف يتطلب تكييفًا موثقًا.
/up يفشل أو Connection refusedافحص حالة الخدمات والمنفذ 8000 قبل الحمل،ثم سجل الخطأ. الصحة الأساسية تسبق القياس،ولا توصف نتيجة اتصال فاشل بأنها تحسين زمن.

503 في تفاصيل المنتجافحص inventory-service واتصال gRPC. التطبيق يرفض تقديم مخزون مختلق، و 503 ليست قراءة منتج ناجحة يجوز خلطها بزمن 200.
INVALID COMPARISONالمقارن وجد endpoint error في أحد التشغيلات. افتح log و JSON وشخص السبب؛ لا تقدم نسبة تحسن من مجموعة فاشلة.

08

خطة عرض قصيرة وقائمة التحضير

تدرب على التسلسل قبل المقابلة.

  1. قبل العرض:تأكد من الخدمات والصور والحساب والمسار،وافتح ملفات المقارنة الأرشيفية.
  2. أمام الأستاذ:عرّف العملية والحمل،واعرض common.js،ثم ابدأ مشغّل dashboard.
  3. خلال التشغيل:اشرح Trend و Rate و setup ولماذا 3 تشغيلات؛ لا تتوقع رقمًا مضمونًا.
  4. بعده:افتح المجلد الجديد،اقرأ الأخطاء،ثم MED والمئينات والمعدل،ثم قارن بالأرشيف مع ذكر الحدود.
  5. عند سؤال الحداثة:اعرض اختبار التعديل المنفصل،وعند سؤال gzip اعرض دليل wire والسيناريو المتخصص.
