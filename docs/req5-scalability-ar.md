# المتطلب الخامس: كيف تعرض التوسّع أمام الدكتور؟

العنوان الذي يراه المستخدم ثابت: `http://127.0.0.1:8015`. خلفه Nginx وثلاث نسخ من Laravel. لا تختَر النسخة في Postman ولا تغيّر العنوان عند توقف حاوية. ثلاث حاويات أخرى تشغّل `orders:email-worker` وتسحب من طابور RabbitMQ نفسه: `orders.email`.

## 1. التشغيل على جهازك أو جهاز زميلك

المتطلبات: Docker Compose حديث، Python 3، وملف `.env` وملفات كلمات مرور MySQL المحلية للمشروع كما في [دليل ما بعد السحب](after-pull-setup.md). تحتاج مفاتيح التطبيق نفسها داخل النسخ الثلاث، ولا تحتاج مفتاح Resend لهذا العرض. نفّذ الأوامر من **WSL / Ubuntu**. على جهاز آخر غيّر المسار في السطر الأول فقط. لا يلزم تشغيل الواجهة لإجراء الاختبار.

```bash
cd /mnt/e/Projects/internet-applications
docker compose -f docker-compose.req5.yml build migrate inventory-service
docker compose -f docker-compose.req5.yml up -d --no-build
docker compose -f docker-compose.req5.yml ps -a
python3 ops/req5/verify.py
```

يجب أن ترى `api-1` و`api-2` و`api-3` وثلاث حاويات `email-worker`. خروج `migrate` بالحالة `0` طبيعي: انتهت مهمته قبل تشغيل النسخ. الاختبار يولّد مستخدماً و150 طلباً تجريبياً في قاعدة `ecommerce_req5` لكل تشغيل؛ يبقي السجلات لتفحصها. البريد محلي وهمي عمداً، ولا يرسل إلى عملاء المشروع. قاعدة بيانات المشروع العادي وخدمة بريده منفصلتان.

على جهاز العرض الحالي، إن كانت الحاويات شغّالة، يكفي `python3 ops/req5/verify.py` من جذر المشروع. التشغيل الذي أنتج التقرير استخدم صور Laravel والمخزون المحلية الجاهزة و`nginx:alpine` و`rabbitmq:3.13-management-alpine`. ملف Compose يحدد افتراضياً `nginx:1.28-alpine` و`rabbitmq:4.2-alpine` للبناء الجديد. التقرير يوثق ما شُغّل فعلاً؛ لا تنقل وحدة بيانات RabbitMQ القديمة بين الإصدارين.

## 2. ماذا تثبت أمام الدكتور؟

1. **التوزيع:** الاختبار يرسل 500 طلب `GET /up` بواسطة 12 عميلاً متزامناً. يربط عنوان `X-Req5-Upstream` في كل إجابة باسم حاوية Docker، ويتحقق أن جميع الإجابات `200` وأن النسخ الثلاث شاركت. `/up` مسار صحة داخل Laravel؛ هذا قياس للتوزيع وليس قياساً لأداء إنشاء الطلبات. يختبر أيضاً `/api/categories` ومسار الزبون المحمي `/api/me` دون تعطيل حدود الطلبات.
2. **الاستمرارية:** يوقف الاختبار `api-1` وحدها، ويتحقق من توقفها فعلاً، ثم يمرر 120 طلباً عبر **العنوان نفسه**. ويطلب `/api/me` برمز الزبون نفسه من النسختين الباقيتين. يعيد تشغيل النسخة حتى إن فشل هذا الجزء من الاختبار، ثم يتأكد أنها عادت إلى التوزيع. بعد تسجيل الخروج يختبر أن النسخ الثلاث ترفض الرمز نفسه بـ`401`.
3. **العمال:** يُنشئ الاختبار 150 حدث `OrderCreated` بمعرّفات مختلفة في جدول الأحداث، ثم يترك الناشر الحقيقي يرسلها إلى RabbitMQ. نطابق معرّفات `notification_deliveries` في MySQL مع سجل **كل عامل على حدة**، ونتحقق أن كل معرّف ظهر مرة في سجل الإنجاز وأن العمال الثلاثة شاركوا. قد تتغير الأعداد من عرض إلى آخر؛ الطابور مشترك ولا تُحجز حصة ثابتة لأي عامل. الاختبار يستعمل بيانات تجريبية مباشرة لاختبار التوزيع، وليس مسار شراء أو إرسال بريد خارجي.
4. **الحالة المشتركة:** يكتب الاختبار من `api-1` علامة في Redis وملفاً في قرص صور المنتجات، ويقرأهما من الثلاث. ويكتب علامة إلى قناة ملف السجل القديمة للمقارنة: تظهر في `api-1` فقط. السجلات الفعلية للعمال الآن تذهب إلى `stderr`، لذلك يمكن عرضها مجتمعة باسم الخدمة مع بقاء اسم كل حاوية واضحاً.

النتائج المسجلة فعلياً، بما فيها صور Docker المستخدمة، موجودة في [req5-evidence.json](req5-evidence.json). بعد كل تشغيل ناجح يُحدّث الاختبار الملف؛ إذا فشل يخرج بخطأ ولا يستبدل التقرير السابق. في Postman استخدم `GET http://127.0.0.1:8015/up` وافتح **Headers → X-Req5-Upstream**. كرّر Send لترى تغيّر العنوان.

### إيقاف نسخة أمام الدكتور يدوياً

بعد انتهاء الاختبار الآلي، نفّذ هذه الأوامر في نافذة WSL نفسها. لا تستعمل `docker compose stop api` لأنه يوقف النسخ الثلاث معاً.

```bash
API_ID=$(docker compose -f docker-compose.req5.yml ps -q api | head -n 1)
docker stop "$API_ID"
docker compose -f docker-compose.req5.yml ps -a api
for i in $(seq 1 8); do curl -sS -o /dev/null -D - http://127.0.0.1:8015/up | grep -Ei '^(HTTP/|X-Req5-Upstream:)'; done
docker start "$API_ID"
docker compose -f docker-compose.req5.yml ps api
```

الخطوة المهمة: كرر طلب Postman **قبل** إعادة تشغيل الحاوية. سترى `200` من العنوانين المتبقيين. بعد إعادة التشغيل انتظر حتى تصبح النسخة `healthy` ثم أعد الطلب عدة مرات. لعرض سجلات العمال:

```bash
docker compose -f docker-compose.req5.yml logs --tail=15 email-worker
```

لإيقاف العرض بعد الانتهاء مع الاحتفاظ ببياناته:

```bash
docker compose -f docker-compose.req5.yml stop
```

## 3. لماذا Round Robin؟

النسخ الثلاث تستخدم صورة Laravel نفسها ولا تحتاج الجلسة إلى نسخة معينة. يوزع Nginx الطلبات على العناوين بأوزان متساوية؛ هذا مناسب هنا لأن النسخ متشابهة، ويسهل تفسير النتيجة. لا يعني هذا أن كل طلب يستهلك الوقت نفسه. إذا اختلفت سعة النسخ أو كثرت الطلبات الطويلة، يمكن عندها مقارنة التوزيع الموزون أو `least_conn` بقياس جديد.

في `nginx.conf` يقرأ `resolve` العناوين الحالية لخدمة `api` من DNS الخاص بـDocker. عند تعذر الاتصال بنسخة، يستطيع Nginx تجربة نسخة أخرى ضمن قيود `proxy_next_upstream`، ويتجنب النسخة المتعطلة مؤقتاً. لم نفعّل إعادة محاولة طلبات الكتابة بعد إرسالها إلى الخلفية؛ إعادة طلب شراء بلا تمييز قد تنشئ أثراً مكرراً. إثباتنا يغطي طلبات القراءة وتوقف نسخة API واحدة؛ Nginx وMySQL وRedis وRabbitMQ والمضيف نفسه ليست مكرّرة في هذا العرض.

## 4. ما الذي تغيّر فعلاً؟ ما الذي كان صحيحاً أصلاً؟

| الحالة | قبل التوسّع | الحل أو القرار | كيف تتحقق؟ |
|---|---|---|---|
| اسم ومنفذ API | `container_name: ecommerce-backend` و`8000:8000` لنسخة واحدة. تجربة `--scale backend=3` أعادت رفض Docker بسبب الاسم. وحتى بعد فك الاسم لا يمكن لثلاث حاويات حجز منفذ المضيف نفسه. | لا اسم ثابت ولا منفذ مضيف للنسخ. Nginx وحده ينشر منفذ HTTP. | `ps -a` ثم توزيع 500 استجابة عبر `8015`. |
| الترحيلات عند الإقلاع | نقطة الدخول تشغّل `artisan migrate` عندما لا يُحدّد `SKIP_MIGRATIONS`. تشغيلها في كل نسخة يعرّض تغييرات المخطط للتزامن؛ هذا خطر ظهر من الكود ولم نسجل تلفاً فعلياً. | خدمة `migrate` واحدة. سائر العمليات تتجاوز الترحيل وتنتظر نجاحه. | `docker compose -f docker-compose.req5.yml logs migrate` و`ps -a migrate`. إعادة نسخة API لا تعيد ترحيل المخطط. |
| سجل Laravel | القناة الافتراضية `stack → single` تكتب في `storage/logs/laravel.log` داخل الحاوية. قراءة ملف حاوية لا تكشف عمل الحاويات الأخرى. | `LOG_CHANNEL=stderr` لكل العمليات. Docker يعرض سجلات النسخ مجتمعة على هذا المضيف. | مقارنة `local_log` في JSON ثم `logs email-worker`: يعرض عمل العمال الثلاثة. الاحتفاظ بالسجلات بعد حذف الحاويات يحتاج خدمة تجميع خارجية. |
| صور المنتجات | `ProductService` يكتب على قرص `public`. المشروع الأصلي كان يربط هذا المسار بوحدة تخزين بالفعل. | أبقينا نفس المبدأ بوحدة مشتركة بين النسخ في بيئة العرض. | `public_file=true` على النسخ الثلاث. هذا القرص مشترك على مضيف Docker واحد؛ عند تشغيل النسخ على أجهزة مختلفة يلزم تخزين مشترك مثل S3. |
| المصادقة والكاش وحدود الطلبات | مفاتيح JWT والكاش في Redis كانت مشتركة أصلاً، والجلسات الافتراضية في قاعدة البيانات وليست ملفات محلية. | نفس `APP_KEY` و`JWT_SECRET` لكل النسخ؛ كاش وجلسات Laravel في Redis واحد. مصادقة API نفسها تستعمل JWT. | نفس الزبون قبل التوقف وأثناءه، ثم `401` عبر الثلاث بعد الخروج. وتقرأ النسخ الثلاث علامة الكاش نفسها. |
| أحداث الطلبات ومنع تكرار البريد | الأحداث في MySQL والطابور في RabbitMQ. منطق الإرسال يحتفظ بحالة التسليم وقفل السطر في قاعدة البيانات أصلاً. | شغّلنا نفس أمر العامل ثلاث مرات على الطابور نفسه، مع ناشر ومجدول منفصلين. لا توجد قائمة رسائل خاصة بذاكرة كل عامل. | 150 معرّفاً في قاعدة البيانات ومطابقة سجل كل عامل. لا ندّعي ضمان إرسال خارجي مرة واحدة في كل حالات الانهيار. |
| ملفات تبقى محلية عمداً | ملفات إعدادات ومسارات Laravel المولّدة وملفات Blade المترجمة قابلة لإعادة الإنشاء. | كل حاوية تعيد بناء ما تحتاجه من نفس الصورة والإعدادات؛ لا نحفظ فيها طلبات أو جلسات زبائن. | أعد تشغيل النسخة ثم أعد `/api/me` عبر البوابة. |

لإعادة فحص **رفض الإعداد القديم**، نفّذ أمر المعاينة التالي؛ الفشل هنا هو النتيجة المنتظرة، ولا يشغّل الأمر حاوية:

```bash
docker compose --dry-run -p ecommerce-req5-before -f docker-compose.yml up -d --no-deps --no-build --scale backend=3 backend
```

## 5. أين الكود؟

- [docker-compose.req5.yml](../docker-compose.req5.yml): عدد النسخ والعمال، المفاتيح والمخازن المشتركة، خدمة الترحيل، المنافذ، وعزل بيئة العرض.
- [nginx.conf](../ops/req5/nginx.conf): اختيار النسخة، اكتشاف تغير عناوينها، معالجة فشل الاتصال، وترويسة الإثبات.
- [verify.py](../ops/req5/verify.py) و[probe.php](../ops/req5/probe.php): قياس التوزيع والتوقف، والتحقق من البيانات والعمال. ملف PHP يُشغّل داخل الحاوية ولا يضيف مسار اختبار إلى API.
- كود موجود يُعاد استخدامه: [نقطة إقلاع Laravel](../backend/my-project/docker-entrypoint.sh)، [حفظ صور المنتجات](../backend/my-project/app/Services/ProductService.php)، [قراءة الطابور](../backend/my-project/app/Services/Messaging/RabbitMqBroker.php)، [تسجيل إتمام الرسالة](../backend/my-project/app/Services/Messaging/EmailMessageProcessor.php)، [منع تكرار تسليم الحدث](../backend/my-project/app/Services/Messaging/OrderConfirmationSender.php).
