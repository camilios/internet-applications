# المتطلب السادس | المراقبة وتتبع الأعطال

## ماذا أفتح أمام الأستاذ؟

افتح [لوحة الطلبات في Grafana](http://127.0.0.1:3006/d/req6-orders/orders?from=now-15m&to=now&refresh=5s) و[قواعد التنبيه](http://127.0.0.1:3006/alerting/list) بجانب الطرفية. اختَر آخر ١٥ دقيقة واترك التحديث كل خمس ثوانٍ. يعمل العرض باسم Docker مستقل هو `ecommerce-req6`. بوابته على 8016، وقواعد بياناته وطوابيره وصندوق بريده مستقلة عن عرضي المتطلبين الرابع والخامس.

### نتيجة العرض المسجّل في ٢٧ تشرين الثاني ٢٠٢٦

| ما تعرضه | ما حدث فعلياً |
|---|---|
| ضغط على البوابة | أعاد التطبيق ٥٠٠ رد ناجح لعشرة عملاء. توزّعت الردود ١٦٦ و١٦٧ و١٦٧. قُرئت بيانات النسخ عبر Grafana في منتصف الاختبار، وكان تقدير p95 نحو ٩٧ ميلي ثانية. رصدت البوابة أيضاً طلب فحص يدوي أُرسل من Windows خلال القياس، ولذلك زاد مجموع عداداتها بمقدار ٥٠١. |
| توقف عمال البريد | استمر الشراء، وتراكمت ست رسائل جاهزة. وصل تنبيه `OrderEmailQueueHigh`، ثم وصل إشعار التعافي بعد إعادة العمال وتصريف الطابور. |
| توقف نسخ API | رصد عميل الاختبار ٦١ ردّاً من فئة 5xx أثناء العطل المتعمّد. وصل تنبيه `HttpErrorsHigh`، ثم عاد HTTP إلى 200 ووصل إشعار التعافي. |
| تتبّع طلب واحد | الطلب رقم ١ يحمل المعرّف `094e7a9f-7914-4683-a6a8-9c4c2aaf9e37`. يظهر في سجل دخول HTTP، وحجز المخزون، ورد 201، وتأكيد النشر، وعامل البريد. وصل تأكيد واحد لهذا الطلب إلى Mailpit. |

افتح [لقطة Grafana المحفوظة لنفس الجولة](req6-dashboard.png). في الرسم الأيمن الأوسط يرتفع الطابور من صفر إلى ستة ثم يعود للصفر، وفي الرسم الأيسر الأوسط تظهر موجة أخطاء البوابة. تجد السجلات المطابقة وفحص السر التجريبي في [تقرير الإثبات](req6-evidence.json). يحتوي التقرير على رابط Grafana مضبوطاً على نافذة الجولة. يحلّ تقرير جديد مكانه بعد كل تجربة ناجحة.

### على جهاز العرض المجهّز

من **Ubuntu / WSL**، إذا كنت بدأت العرض بالصور الموجودة والكود المحلي على جهاز ملاد، فهذه هي أوامر التشغيل والإثبات:

```bash
cd /mnt/e/Projects/internet-applications
bash ops/req6/compose.sh --local-sources up -d --no-build --pull never --wait
python3 ops/req6/verify.py --monitoring-only
python3 ops/req6/verify.py
```

اترك نافذة Ubuntu مفتوحة طوال العرض. يؤكّد الخيار `--monitoring-only` وجود اللوحة وقاعدتي التنبيه ونجاح جمع المقاييس من البوابة والوسيط. أما التشغيل الأخير فينشئ ستة طلبات شراء تجريبية، ويوقف خدمات العرض ويرجعها تلقائياً. بعد رجوع API يستطيع طلب جديد النجاح فوراً، بينما يحتاج تنبيه الأخطاء إلى خروج الردود السابقة من نافذة الدقيقة حتى يصل إشعار التعافي. تُسلَّم رسائل العرض إلى [صندوق Mailpit المحلي](http://127.0.0.1:8026).

### تجهيز جهاز آخر

يتطلب هذا العرض Docker Compose الداعم لـ `!override` (٢٫٢٤٫٤ أو أحدث)، وPython 3.9 أو أحدث، وملف بيئة المشروع وملفات أسرار قواعد البيانات المعتادة. خذ خطوات إعدادها من [دليل ما بعد السحب](after-pull-setup.md). من جذر المشروع في Ubuntu:

```bash
# مرة واحدة إذا لم تكن صورة Laravel للمتطلب الخامس مجهّزة مسبقاً
docker compose -f docker-compose.req5.yml build migrate

# ابْنِ خدمات المتطلب السادس من كود المشروع
bash ops/req6/compose.sh build migrate inventory-service
bash ops/req6/compose.sh up -d --no-build --wait
python3 ops/req6/verify.py --monitoring-only
python3 ops/req6/verify.py
```

في وضع الصور الجاهزة `--local-sources` يستخدم السكربت صور حاويات المتطلب الخامس الموجودة، ويربط مصدر Laravel وملفات JavaScript المترجمة للقراءة فقط. إذا عدّلت خدمة المستودع، نفّذ `npm ci` ثم `npm run build` داخل `inventory-service` قبل تشغيل هذا الوضع. في طريقة البناء العادية ينفّذ Docker ترجمة TypeScript داخل الصورة. يخصص المعمل ذاكرة صغيرة لقاعدتي البيانات. خدمات الجدولة وبث الواجهة لها ملف تشغيل اختياري اسمه `realtime`، لأن العرض يمرّ عبر HTTP والمستودع وطابور البريد.

## ١. كيف أري توزيع الطلبات وزمن الاستجابة والأخطاء؟

يرسل الاختبار ٥٠٠ طلب `GET /up` بعشرة عملاء عبر Nginx. راقب منحنى **Requests by API replica**. لكل عنوان داخلي منحنى، ويزداد العدد على النسخ الثلاث. يعطي **Requests per second** معدل الوصول، ويعرض **Response time · p95** الزمن الذي اكتمل خلاله نحو ٩٥٪ من الردود. يقيس Nginx الزمن من جهة العميل ويشمل إعادة المحاولة الداخلية. إذا اتصل بأكثر من نسخة يُنسب الرد النهائي إلى آخر عنوان اتصل به. وتُحسب أخطاء البوابة نفسها حتى عندما تتوقف جميع نسخ Laravel.

افتح [تنسيق سجل Nginx](../ops/req6/nginx-format.conf)، ثم [مجمّع المقاييس](../ops/req6/http-metrics.mjs) و[تعريف اللوحة](../ops/req6/grafana/dashboards/orders.json). يسجّل Nginx حالة HTTP والمدة وعنوان النسخة. يجمع المصدّر العدادات وحاويات المدد الزمنية، ويسحبها Prometheus دورياً. مسار Syslog المحلي يستخدم UDP، ويمكن أن يفقد عينات تحت ضغط شديد. لذلك يقارن اختبار العرض الردود التي استلمها العميل بما رصده Prometheus. [توثيق Nginx](https://nginx.org/en/docs/syslog.html)

## ٢. كيف ينطلق التنبيهان؟

| ما يفعله الاختبار | ما تراه | كيف تفسّر النتيجة؟ |
|---|---|---|
| يوقف عمّال البريد الثلاثة ثم ينشئ ستة طلبات | يرتفع عدد الرسائل الجاهزة في `orders.email`. يظهر `OrderEmailQueueHigh`، ثم يصل إشعار `firing` إلى مستقبل التنبيهات | حد الإنذار في العرض خمس رسائل جاهزة لمدة عشر ثوانٍ. لقد استمر الشراء بينما تراكم العمل المؤجل. |
| يعيد العمّال ثم يوقف نسخ API الثلاث ويرسل طلبات إلى البوابة | يرتفع منحنى 5xx ويصل `HttpErrorsHigh` | القاعدة تتطلب ثلاث أخطاء خادم على الأقل ونسبة أعلى من ٥٪ خلال دقيقة، مع استمرار الشرط عشر ثوانٍ. إيقاف النسخ الثلاث يولّد أخطاء حقيقية يراها العميل. |
| يعيد نسخ API وينتظر تصريف الطابور وانتهاء نافذة الأخطاء | يعود HTTP إلى 200 وتصل إشعارات `resolved` | عاد الشرط إلى وضعه الطبيعي. يقيس السكربت وصول الإشعار إلى جهة الاستلام. |

في نافذة Ubuntu ثانية يمكنك مشاهدة إشعارات التنبيه عند وصولها. افتحها **قبل** تشغيل الاختبار:

```bash
cd /mnt/e/Projects/internet-applications
bash ops/req6/compose.sh logs -f --tail=0 http-metrics
```

تقرأ [إعدادات Prometheus](../ops/req6/prometheus.yml) حجم الطابور من إضافة RabbitMQ على المنفذ الداخلي 15692. يضم **Email queue depth** الرسائل الجاهزة وتلك التي سلّمها الوسيط ولم يتلقَّ تأكيدها بعد. ويمثل **Email messages waiting** الرسائل الجاهزة فقط. تستخدم [قواعد Grafana](../ops/req6/grafana/provisioning/alerting/rules.yaml) هذه البيانات وتوصل [جهة الاتصال](../ops/req6/grafana/provisioning/alerting/contact.yml) الإشعار إلى مستقبل محلي يسجله بصيغة JSON. [توثيق مقاييس RabbitMQ](https://www.rabbitmq.com/docs/prometheus)

## ٣. كيف أتتبع طلب زبون واحد؟

بعد نجاح الاختبار تجد رقم الطلب و`correlation_id` في `docs/req6-evidence.json`. ابحث عنه في الخدمات معاً:

```bash
TRACE=$(python3 -c "import json; print(json.load(open('docs/req6-evidence.json'))['correlation_id'])")
bash ops/req6/compose.sh logs --no-color api inventory-service outbox-publisher email-worker | grep -F "$TRACE"
```

| المرحلة | أين تبحث في الكود؟ | ما الذي يربطها بالمرحلة التالية؟ |
|---|---|---|
| بدأ طلب HTTP | [TraceRequest](../backend/my-project/app/Http/Middleware/TraceRequest.php) | يقبل UUID صالحاً من `X-Correlation-ID` أو يولّد واحداً، ويعيده في ترويسة الرد. |
| حُجز المخزون | [عميل gRPC](../backend/my-project/app/Services/InventoryGrpcClient.php) و[معالجات المستودع](../inventory-service/src/grpc/handlers.ts) | يسافر المعرّف في metadata. يظهر `ReserveStock` والنتيجة ومعرّف التتبع في سجل المستودع. |
| حُفظ الطلب | [OrderService](../backend/my-project/app/Services/OrderService.php) | تُحفظ قيمة التتبع في حمولة Outbox مع `event_id` و`order_id`. لذلك تبقى متاحة بعد انتهاء طلب HTTP. |
| قَبِل RabbitMQ الحدث | [OutboxPublisher](../backend/my-project/app/Services/Messaging/OutboxPublisher.php) | يُسجّل الناشر معرّف التتبع مع رقم الطلب ومعرّف الحدث. |
| عولج البريد | [معالج الرسالة](../backend/my-project/app/Services/Messaging/EmailMessageProcessor.php) و[خدمة الإرسال](../backend/my-project/app/Services/Messaging/OrderConfirmationSender.php) | يستعيد العامل المعرّف من الرسالة، ويسجّل قبول ناقل البريد ثم انتهاء المعالجة. يطابق الاختبار رقم الطلب برسالة في صندوق SMTP. |

`correlation_id` يربط رحلة HTTP بالعمل اللاحق. يعرّف `event_id` رسالة الشراء حتى عند تكرار تسليمها، أما `order_id` فهو الرقم الذي يراه الزبون. للأحداث القديمة التي لا تحتوي معرّف تتبع يستخدم العامل والناشر معرّف الحدث لربط مرحلتي البريد.

## ٤. كيف أثبت حماية البيانات؟

يسمح [منسّق Laravel](../backend/my-project/app/Logging/SafeJsonFormatter.php) بمجموعة محددة من أسماء الأحداث والحقول. يمكن حفظ نوع الاستثناء ورقم الطلب والحالة، بينما تُستبعد رسالة الاستثناء الخام والترويسات ومحتوى الطلب. يطبّق المستودع والبوابة مبدأ اختيار الحقول أيضاً. لا تسجّل دخول الزبون أو بريده لتحديد رحلة الطلب، فمعرّف التتبع يكفي.

يرسل اختبار الإثبات قيمة تجريبية مميزة ككلمة مرور وترويسة وملف تعريف ارتباط ومعامل في الرابط، ثم يبحث عنها وعن رمز دخول زبون التجربة في سجلات البوابة والتطبيق والمستودع والناشر والعامل. يفشل الاختبار إن ظهرت إحدى القيمتين. ويختبر [اختبار Laravel](../backend/my-project/tests/Feature/ObservabilityTest.php) استثناءً يحتوي بيانات حساسة وحقولاً متداخلة أيضاً.

عند ظهور `PASS` افتح ملف الدليل الذي طبعه السكربت. يتضمن العدادات حسب النسخة، وp95، والتنبيهين، ومراحل الطلب بصيغة JSON، ورابط Grafana مضبوطاً على زمن الجولة. يحتفظ Prometheus بالبيانات في وحدة تخزين المشروع. وبعد انتهاء العرض، إذا أردت إيقاف هذه البيئة وحدها:

```bash
bash ops/req6/compose.sh stop
```
