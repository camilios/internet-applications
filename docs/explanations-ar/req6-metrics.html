١. من أين يأتي كل رقم؟

HTTP client → Nginx
                 ├─ proxies HTTP → Laravel API replica
                 └─ sends status + duration + upstream over UDP → Node exporter :9108/metrics
                                                                              ↓
RabbitMQ :15692/metrics/per-object ───────────────────────────────────────→ Prometheus
                                                                              ↓ PromQL
                                                                           Grafana

للطلب مسار عادي من العميل إلى Nginx ثم إلى نسخة Laravel. عندما يكتمل الرد، يعرف Nginx عنوان آخر نسخة حاول الاتصال بها وحالة الرد والمدة التي استغرقها من جهة البوابة. يرسل هذه القيم الثلاث إلى مجمّع Node، الذي يحوّلها إلى عدادات وحاويات زمنية. يقرأ Prometheus هذه الأرقام من المجمّع كل خمس ثوانٍ.

يعرف RabbitMQ وحده عدد الرسائل المنتظرة وعدد الرسائل التي تسلّمها عامل ولم يؤكّدها بعد. لذلك يسحب Prometheus حجم الطابور مباشرة من إضافة RabbitMQ. تقرأ Grafana المصدرين من Prometheus باستعلامات PromQL وتعرضهما على محور زمني واحد.

ما الذي يثبته العرض؟ من نفس جولة الاختبار سترى عدد الردود لكل نسخة وزمنها، وارتفاع الأخطاء عند توقف API، وتراكم الرسائل عند توقف العمال ثم تصريفها بعد رجوعهم.

gateway.ports و!override
تنشر البوابة التي داخل الحاوية على منفذ 80 بعنوان 127.0.0.1:8016 على الجهاز. تستبدل !override قائمة المنافذ الموروثة حتى يستعمل هذا العرض منفذه المحدد. السطران في volumes يركبان ملف شكل السجل وملف تشغيله للقراءة فقط. depends_on ينتظر نجاح فحص المجمّع عند تشغيل البوابة.
rabbitmq.environment وrabbitmq.volumes
يحدد RABBITMQ_ENABLED_PLUGINS_FILE المكان الذي يقرأ منه الوسيط قائمة الإضافات. يضع الـmount الملف في المسار ذاته. خيارات Erlang تحدّ من عدد منافذ جدولة التنفيذ داخل البيئة التجريبية. سطر Mailpit المجاور يغيّر منفذ واجهة البريد الظاهرة إلى 8026 في هذا المشروع.
http-metrics وnetworks
يشغّل Docker السكربت المربوط باستخدام Node 22. له عنوان ثابت 172.30.65.10 على شبكة edge لتستطيع البوابة إرسال UDP إليه. وهو متصل أيضاً بالشبكة الافتراضية حتى يستطيع Prometheus الوصول إليه باسم http-metrics. فحص الصحة يقرأ /metrics دورياً من داخل حاوية المجمّع. حالة healthy تثبت أن endpoint صالح للقراءة حتى في أول تشغيل، قبل ظهور بيانات الحمل.

٤. لماذا أخذنا الحالة والزمن وعنوان النسخة من Nginx؟

كل عميل في العرض يمرّ من البوابة. لذلك نستخدم زمن الطلب الذي تقيسه البوابة وحالة الرد الذي تُرسله. تستطيع البوابة تسجيل رد 502 حتى عندما لا تصل أي محاولة إلى Laravel. كما أنها تملك معلومة النسخة التي حاولت الاتصال بها، فتصلح نقطة جمع واحدة للنسخ الثلاث.

  • الترويسة الموجودة أصلاً X-Req5-Upstream تكشف $upstream_addr في رد العميل. يستخدمها سكربت الإثبات لمقارنة عدّه بعدادات Prometheus. تستعمل البوابة المتغيّر نفسه في سجلها الداخلي.

٥. كيف يتحول سجل HTTP إلى Counter وHistogram؟

هياكل البيانات واستقبال قياس واحد

افتح ops/req6/http-metrics.mjs · الأسطر 1–24

import dgram from 'node:dgram'
import http from 'node:http'
import { isIPv4 } from 'node:net'

const buckets = [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 15, 60]
const replicas = new Map()
const notifications = new Map()
const alertNames = new Set(['OrderEmailQueueHigh', 'HttpErrorsHigh'])

function observe({ upstream, status, seconds }) {
  if (!Number.isInteger(status) || status < 100 || status > 599 ||
      !Number.isFinite(seconds) || seconds < 0 || typeof upstream !== 'string') return
  // Nginx may have retried. Charge one client response to the final contacted upstream.
  const address = upstream.match(/(\d+\.\d+\.\d+\.\d+):8000$/)?.[1]
  const replica = address && isIPv4(address) ? address : 'gateway'
  if (!replicas.has(replica)) {
    replicas.set(replica, { codes: new Map(), count: 0, sum: 0, buckets: buckets.map(() => 0) })
  }
  const stats = replicas.get(replica)
  stats.codes.set(status, (stats.codes.get(status) ?? 0) + 1)
  stats.count++
  stats.sum += seconds
  buckets.forEach((bound, i) => { if (seconds <= bound) stats.buckets[i]++ })
}
الأسطر ١–٣
توفر dgram استقبال UDP، وhttp نقطة القراءة لـPrometheus، وisIPv4 فحص أن القيمة المستخرجة تصلح عنوان نسخة.
الأسطر ٥–٨
تحدد buckets حدود الزمن بالثواني، مثل 0.005 وهي 5 ميلي ثانية. تخزّن replicas العدّادات لكل عنوان. يرتبط notifications وalertNames بتوثيق وصول التنبيه في المجمّع نفسه.
الأسطر ١٠–١٥
تقرأ دالة observe الحقول الثلاثة بأسمائها. تتحقق من أن الحالة عدد صحيح ضمن نطاق HTTP، وأن الزمن عدد صالح غير سالب، وأن قيمة upstream نص. يختار التعبير الذي ينتهي بـ$ آخر عنوان IPv4 تابع لمنفذ 8000 في السجل، وينسب إليه الرد النهائي مرة واحدة. إذا تعذّر استخراج ذلك العنوان، يظهر الرد ضمن سلسلة gateway.
الأسطر ١٦–٢٣
يهيئ مدخلاً عند أول رد من عنوان. codes خريطة عدّ لكل حالة، ويسمح ?? 0 بالبدء من صفر عند أول ظهور للحالة. يزيد count بمقدار واحد، ويضيف المدة إلى sum، ثم يزيد كل حاوية حدها أكبر من المدة أو يساويها.
مثال، رد 200 من 172.30.65.3:8000 خلال 0.083 ثانية يرفع عداد 200 لتلك النسخة بمقدار واحد. الحاويتان le="0.025" وle="0.05" لا تتغيران بهذا القياس. من le="0.1" فما فوق تزيد كل حاوية واحداً، ويزداد المجموع الزمني بـ0.083. هكذا تصبح الحاويات تراكمية.

تحويل العدادات إلى النص الذي يقرأه Prometheus

افتح ops/req6/http-metrics.mjs · الأسطر 26–41

function metrics() {
  const lines = ['# TYPE order_http_requests_total counter', '# TYPE order_http_duration_seconds histogram',
    '# TYPE order_alert_notifications_total counter']
  for (const [replica, stats] of replicas) {
    const labels = 'replica="' + replica + '"'
    for (const [status, count] of stats.codes) {
      lines.push('order_http_requests_total{' + labels + ',status="' + status + '"} ' + count)
    }
    buckets.forEach((bound, i) => lines.push('order_http_duration_seconds_bucket{' + labels + ',le="' + bound + '"} ' + stats.buckets[i]))
    lines.push('order_http_duration_seconds_bucket{' + labels + ',le="+Inf"} ' + stats.count,
      'order_http_duration_seconds_count{' + labels + '} ' + stats.count,
      'order_http_duration_seconds_sum{' + labels + '} ' + stats.sum)
  }
  for (const [labels, count] of notifications) lines.push('order_alert_notifications_total{' + labels + '} ' + count)
  return lines.join('\n') + '\n'
}
# TYPE وتسميات السلسلة
يصف كل سطر نوع المقياس. order_http_requests_total عداد تصاعدي؛ يوجد سطر منفصل لكل زوج replica,status. يكتب الكود أسطره من القيم المحسوبة في observe عند طلب المقاييس.
_bucket وle
كل سطر يصف حاوية ويعطي حدها الأعلى في تسمية le. حد +Inf يشمل كل القياسات مهما كان زمنها، لذلك قيمته تساوي _count. يحفظ _sum إجمالي الثواني. تستعمل لوحة p95 الحاويات وحدودها لحساب تقدير المئين.
join('\n')
يضع كل مقياس في سطر ويختم النص بسطر جديد حسب صيغة exposition النصية. تُحفظ العدادات الحالية في ذاكرة المجمّع. بعد إعادة تشغيله يبدأ عدّ جديد، وتبقى العينات التي سبق أن حفظها Prometheus في وحدة تخزينه.

        regex: 'rabbitmq_queue_messages(_ready|_unacked)?'
        action: keep
scrape_interval: 5s وscrape_timeout: 4s
يبدأ Prometheus أخذ عينة كل خمس ثوانٍ لكل هدف. يسمح بأربع ثوانٍ لإتمام السحب. يمكن أن ترى فرقاً قصيراً بين وقت حدوث الرد ووقت ظهوره في الرسم، لأن عرض Grafana له دورة تحديث مستقلة أيضاً.
job_name: gateway
اسم المهمة الظاهر في Targets. الهدف الحقيقي هو المصدّر http-metrics:9108، فيستعمل المسار الافتراضي /metrics.
job_name: rabbitmq
المهمة الثانية تصل إلى إضافة الوسيط باسم الخدمة داخل Docker. بعد السحب يقرأ metric_relabel_configs اسم كل مقياس من __name__ ويحفظ المطابق فقط، أي عمق الطابور الكلي أو الجاهز أو غير المؤكد. يظل لطوابير الوسيط أكثر من سلسلة، ويضيق استعلام اللوحة الاختيار إلى orders.email.
قراءة قيم الطابور
messages_ready رسائل تنتظر مستهلكاً. messages_unacked رسائل خرجت من قائمة الانتظار وهي لدى مستهلك لم يؤكدها. messages هو مجموعهما. هذه القيم Gauges يمكن أن تصعد مع إنشاء الطلبات وتهبط مع معالجة البريد.

Requests by API replicasum by (replica) (order_http_requests_total)يجمع حالات HTTP بحسب عنوان replica. كل نقطة قيمة تراكمية منذ بدء تشغيل المجمّع. يظهر عنوان gateway عند تعذّر استخراج عنوان API.

افتح ops/req6/compose.sh · الأسطر 1–23

#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/../.."
# Use the prepared Req5 runtime when present. Fresh checkouts can build its standard images first.
for pair in 'APP_IMAGE api' 'NGINX_IMAGE gateway' 'RABBIT_IMAGE rabbitmq' 'INVENTORY_IMAGE inventory-service'; do
  read -r suffix service <<< "$pair"
  variable="REQ5_$suffix"
  if [[ -z "${!variable:-}" ]]; then
    if runtime=$(docker inspect -f '{{.Config.Image}}' "ecommerce-req5-${service}-1" 2>/dev/null); then
      export "$variable=$runtime"
    fi
  fi
done
files=(-f docker-compose.req5.yml -f docker-compose.req5-interview.yml -f docker-compose.req6.yml)
if [[ ${1:-} == --local-sources ]]; then
  shift
  if [[ ! -s inventory-service/dist/grpc/handlers.js || inventory-service/src/grpc/handlers.ts -nt inventory-service/dist/grpc/handlers.js ]]; then
    echo 'Compile inventory-service first (npm run build inside inventory-service).' >&2
    exit 1
  fi
  files+=(-f ops/req6/local-sources.yml)
fi
exec docker compose -p ecommerce-req6 "${files[@]}" "$@"

افتح ops/req6/verify.py · الأسطر 84–95

def monitoring():
    until(lambda:http(GRAFANA+'/api/health')[0]==200,'Grafana startup')
    until(lambda:http(PROM+'/-/ready')[0]==200,'Prometheus startup')
    dashboard = get_json(GRAFANA+'/api/dashboards/uid/req6-orders')['dashboard']
    targets = until(lambda: (points if len(points := query('up{job=~"gateway|rabbitmq"} == 1')) == 2 else None),
                    'both Prometheus targets')
    rules = get_json(GRAFANA+'/api/prometheus/grafana/api/v1/rules')['data']['groups']
    names = {r['name'] for group in rules for r in group['rules']}
    if not {'OrderEmailQueueHigh', 'HttpErrorsHigh'} <= names:
        raise RuntimeError('Expected both provisioned rules')
    return {'dashboard':dashboard['title'],'panels':len(dashboard['panels']),
            'targets':[p['metric']['job'] for p in targets],'rules':sorted(names)}

ينتظر الفحص واجهتي الصحة، ثم يطلب تعريف اللوحة بواسطة UID، ويستعلم عن up ويتحقق أن النتيجة الجاهزة تحوي الهدفين. يأخذ أسماء القواعد من Grafana ويعيد ملخصاً. حتى هذه الخطوة يكون الدليل هو الاتصال والتهيئة. يبدأ إثبات تغيّر الأرقام في الخطوة التالية.

  1. في Grafana افتح اللوحة، واجعل المجال Last 15 minutes والتحديث 5s. يمكنك استخدام Last 5 minutes لتكبير وقت التجربة. رتّب نافذة المتصفح بجانب نافذة Ubuntu. فتح لوحة الطلبات

افتح ops/req6/verify.py · الأسطر 134–183

    def totals():
        return {p['metric']['replica']:int(float(p['value'][1]))
                for p in query('sum by(replica) (order_http_requests_total{status="200",replica!="gateway"})')}
    # Seed a baseline for each series before applying load, including on a fresh stack.
    def read_replica():
        status, headers, _ = http(BASE+'/up')
        if status != 200:
            raise RuntimeError(f'Load request returned HTTP {status}')
        address = headers.get('X-Req5-Upstream', '').split(',')[-1].strip()
        if not address.endswith(':8000'):
            raise RuntimeError('Missing API address on a successful response')
        return address[:-5]

    initial = totals()
    warmup = Counter(read_replica() for _ in range(9))
    if len(warmup) != 3:
        raise RuntimeError('Warmup did not reach three API replicas')
    def baseline():
        current = totals()
        return current if all(current.get(ip,0) >= initial.get(ip,0)+n for ip,n in warmup.items()) else None
    before = until(baseline, 'replica counters after warmup')
    remaining = 500
    client_counts = Counter()
    dashboard_query = 'sum by (replica) (order_http_requests_total)'
    with ThreadPoolExecutor(max_workers=10) as pool:
        while remaining:
            batch = min(25, remaining)
            client_counts.update(pool.map(lambda _: read_replica(), range(batch)))
            remaining -= batch
            if remaining == 250:
                proxy = GRAFANA+'/api/datasources/proxy/uid/req6-prom/api/v1/query?'
                sample = get_json(proxy+urlencode({'query':dashboard_query}))['data']['result']
                report['grafana_during_load'] = {p['metric']['replica']:float(p['value'][1]) for p in sample}
                if len(report['grafana_during_load']) < 3:
                    raise RuntimeError('Grafana did not return all three replica series during load')
            time.sleep(.45)
    if sum(client_counts.values()) != 500 or set(client_counts) != set(warmup):
        raise RuntimeError('Expected 500 successful load requests')
    report['client_http_200'] = dict(client_counts)
    def load_seen():
        current = totals()
        delta = {ip:current.get(ip,0)-before[ip] for ip in client_counts}
        return delta if all(delta[ip] >= n for ip,n in client_counts.items()) else None
    report['load_200_by_replica'] = until(load_seen,'Prometheus load per replica')
    points = until(lambda:query('histogram_quantile(0.95,sum by(le)(rate(order_http_duration_seconds_bucket[1m])))'),
                   'response-time histogram')
    report['p95_seconds'] = float(points[0]['value'][1])
    if not (0 <= report['p95_seconds'] < float('inf')):
        raise RuntimeError('No finite latency sample')
    print('Load shown on Grafana:', report['load_200_by_replica'], flush=True)

totals() تجمع عداد 200 بحسب النسخة وتستبعد سلسلة البوابة. read_replica() يتأكد من 200 ويقرأ آخر عنوان في ترويسة Nginx ويحذف لاحقة :8000. أُخذت نقطة بداية بعد الإحماء حتى يكون الفرق للدفعة. داخل الحلقة يسأل السكربت Grafana عبر datasources/proxy/uid/req6-prom بعد إرسال 250 طلباً. وفي النهاية يطرح before من القراءة الحالية للنسخ، ثم يشترط أن تكون الزيادة لكل نسخة على الأقل عدد ردودها التي شاهدها العميل. الاستعلام الأخير يجمع كل الحاويات الزمنية حسب le ويحسب p95 إجمالياً، بينما رسم Grafana يحافظ أيضاً على replica ويعرض p95 لكل سلسلة.
