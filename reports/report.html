2. مراجعة المعمارية والتصميم الهندسي (Architecture & Design Review)

تتبع منظومة المتطلب الرابع في مشروع SEE معايير هندسية متقدمة في معالجة النظم الموزعة، حيث تم عزل العمليات المتزامنة عن العمليات غير المتزامنة باستخدام نمط Transactional Outbox لتفادي مشكلات الفشل الجزئي (Dual-Write Problem).

مخطط مسار البيانات ومعمارية المعالجة غير المتزامنة (Asynchronous Pipeline):

+------------------+ 1. HTTP POST /api/orders | Customer Client | ----------------------------------------+ +------------------+ | v +-----------------------------------------------------------------------------------+ | Laravel Backend (OrderService) | | | | DB::transaction(function() { | | 1. Save Order to 'orders' table | | 2. Save Items to 'order_items' table | | 3. Insert Outbox Record into 'outbox_events' table (event_id: UUID) | | }); | | | | DB::afterCommit(function() { | | event(new OrderCreated($order)); // Dispatched to 'broadcasts' DB Queue | | }); | +-----------------------------------------------------------------------------------+ | +-----------------+-----------------+ | (DB Outbox Row) | (After Commit) v v +-----------------------------+ +-----------------------------+ | Outbox Publisher Worker | | Broadcast Worker | | (php artisan outbox:publish)| | (queue:work --broadcasts) | +-----------------------------+ +-----------------------------+ | | | Publisher Confirms | Pushes event via | Delivery Mode: Persistent | Pusher Protocol v v +-----------------------------+ +-----------------------------+ | RabbitMQ Broker (vhost: /) | | Laravel Reverb (Port: 8080) | | Exchange: orders.events | | WebSocket Server | | Queue: orders.email (Quorum)| +-----------------------------+ +-----------------------------+ | | | Real-Time Broadcast | Basic Get / Manual Ack | (JWT Authorized) v v +-----------------------------+ +-----------------------------+ | Email Worker | | Frontend (Laravel Echo) | | (orders:email-worker) | | - Admin: admin.orders | +-----------------------------+ | - Customer: orders.{id} | | +-----------------------------+ +-----------------+-----------------+ | (Success) | (Failure) v v +------------------------+ +----------------------------------------------+ | 1. Record Delivery in | | 1. Increment attempts header | | notification_ | | 2. If < 5: Route to 'orders.retry' (TTL) | | deliveries table | | 3. If >= 5 or fatal: Route to 'orders.dlq' | | 2. ACK message | | 4. ACK message from main queue | +------------------------+ +----------------------------------------------+

تحليل مكونات التصميم:

  • Transactional Outbox Pattern: يتم حفظ الحدث outbox_events في نفس المعاملة (Database Transaction) الخاصة بحفظ الطلب وعناصره. يمنع هذا التصميم فقدان الرسائل نهائياً إذا تعطل وسيط الرسائل RabbitMQ أو شبكة الاتصال أثناء إنشاء الطلب.
  • عامل النشر المستقل (OutboxPublisher): يقرأ الأحداث المعلقة باستخدام lockForUpdate() لمنع التنافس (Race Conditions)، ويستخدم confirm_select() لضمان تأكيد استلام RabbitMQ للرسالة قبل تحديث حقل published_at.
  • طوابير Quorum والرسائل الدائمة: تستخدم طوابير RabbitMQ نوع x-queue-type: quorum، ويتم وسم الرسائل بـ delivery_mode: 2 (Persistent)، مما يضمن كتابتها على القرص واستعادتها حتى في حال انهيار خادم RabbitMQ فجأة.
  • آلية التحقق من التكرار (Idempotency): يستخدم OrderConfirmationSender جدول notification_deliveries مقترناً بمفتاح event_id (UUID فريد). في حال إعادة إرسال الرسالة من RabbitMQ بسبب انقطاع الاتصال قبل الـ ACK، يتحقق العامل من وجود السجل في قاعدة البيانات، ويتخطى إرسال البريد المكرر فوراً.

5. مراجعة الأمان والتحكم بالوصول (Security & Authorization Review)

تعد حماية قنوات البث الفوري من أهم متطلبات الأمان في منصات التجارة الإلكترونية، لمنع تسريب بيانات العملاء وتفاصيل الطلبات والمبالغ المالية إلى أطراف غير مصرح لها.

أ. آلية مصادقة قنوات الويب سوكت (WebSocket Authentication):

يستخدم النظام نقطة النهاية المخصصة /broadcasting/auth المحمية بحارس المصادقة auth:api (JWT Auth). عند اتصال عميل الواجهة الأمامية عبر مكتبة pusher-js / laravel-echo، يتم إرسال رمز المصادقة في ترويسة الطلب:

// Authorization Header sent by Echo Client Authorization: Bearer <JWT_ACCESS_TOKEN>

ب. قواعد تفويض القنوات في ملف routes/channels.php:

  • قناة الإدارة الخاصة (admin.orders):
    Broadcast::channel('admin.orders', fn (User $user): bool => $user->role === 'admin', ['guards' => ['api']]);
    تضمن هذه القاعدة عدم قدرة أي حساب بدور customer على الاشتراك أو التقاط إشعارات إنشاء الطلبات الشاملة للمتجر. تم إثبات عملها واختبارها بإرجاع 403 Forbidden عند محاولة العميل العادي.
  • قناة الطلب الخاصة بالعميل (orders.{orderId}):
    Broadcast::channel('orders.{orderId}', function (User $user, string $orderId): bool { return ctype_digit($orderId) && Order::query()->useWritePdo() ->whereKey($orderId)->where('user_id', $user->getKey())->exists(); }, ['guards' => ['api']]);
    تضمن هذه القاعدة:
    1. أن معرف الطلب رقمي صحيح (ctype_digit) لمنع حقن الاستعلامات.
    2. استخدام useWritePdo() للقراءة المباشرة من قاعدة البيانات الأساسية لتفادي مشكلات تأخر النسخ المتطابق (Replication Lag).
    3. التحقق الصارم من أن الطلب يخص المستخدم الحالي (user_id == user->getKey()). محاولة فتح طلب مستخدم آخر تُرفض تلقائياً بـ 403 Forbidden.

ج. أمان وسيط الرسائل RabbitMQ:

  • عزل الاتصال: يعمل RabbitMQ داخل شبكة Docker المعزولة، ولا يتم كشف المنافذ الحساسة خارج بيئة التطوير.
  • مستخدم مخصص: يتم استخدام بيانات اعتماد محددة عبر متغيرات البيئة RABBITMQ_USER و RABBITMQ_PASSWORD، مع دعم عزل البيئات عبر vhosts منفصلة للاختبارات (مثل req4.test).

6. مراجعة الموثوقية واستمرارية الخدمة (Reliability & Fault Tolerance)

تم فحص الإجراءات المتبعة للتعامل مع حالات الانهيار (Crashes)، انقطاع الشبكة، وازدواجية الرسائل، لضمان استمرارية عمل النظام دون فقدان البيانات:

1. نمط الصندوق الصادر المعاملي (Transactional Outbox):

في App\Services\OrderService::createOrder، يتم تسجيل الحدث في جدول outbox_events في قاعدة البيانات ضمن نفس المعاملة (ACID Transaction) التي تسجل الطلب وعناصره. يترتب على ذلك:

  • إذا فشلت قاعدة البيانات في تسجيل الطلب، لا يتم إنشاء أي حدث outbox.
  • إذا نجح تسجيل الطلب وفشل وسيط RabbitMQ، يظل الحدث محفوظاً في جدول outbox_events بحالة غير منشورة (published_at IS NULL).
  • يقوم OutboxPublisher بإعادة محاولة النشر بمجرد عودة RabbitMQ للعمل، دون أي تدخل يدوي.

2. تأكيد النشر وقفل التزامن (Publisher Confirms & Row Locking):

في App\Services\Messaging\OutboxPublisher، يتم جلب الرسائل المعلقة باستخدام:

OutboxEvent::query()->whereNull('published_at')->orderBy('id')->limit(50)->lockForUpdate()->get();

يضمن lockForUpdate() عدم قيام عمال متوازيين بنشر نفس الحدث في نفس اللحظة. كما يتم استدعاء $channel->confirm_select() و wait_for_pending_acks_returns() لضمان أن RabbitMQ قام بكتابة الرسالة في طابور Quorum على القرص الصلب قبل وضع علامة النشر في قاعدة البيانات.

3. طوابير Quorum والرسائل الدائمة:

تستخدم الطوابير الوسيطة إعداد x-queue-type: quorum المعتمد على خوارزمية Raft للإجماع الموزع، مما يوفر مقاومة عالية لفقدان البيانات، مع تفعيل DELIVERY_MODE_PERSISTENT على كافة الرسائل الصادرة.

4. الاستهلاك اليدوي (Manual Acknowledgments):

في OrderEmailWorker، يتم استهلاك الرسائل بضبط no_ack = false. لا يرسل العامل إشارة ack إلى RabbitMQ إلا بعد أن ينجح OrderConfirmationSender في إرسال البريد وحفظ سجل التسليم، أو بعد أن يتم تحويل الرسالة الفاشلة إلى طابور DLQ. في حال انهيار حاوية العامل في منتصف التنفيذ، يعيد RabbitMQ الرسالة فوراً إلى مقدمة الطابور لمعالجتها من قبل عامل آخر.

5. معالجة التكرار (Idempotency Control):

لتفادي إرسال أكثر من بريد إلكتروني لنفس الطلب عند إعادة تسليم الرسائل، يقوم OrderConfirmationSender بفحص جدول notification_deliveries:

$existing = NotificationDelivery::query()->where('event_id', $eventId)->lockForUpdate()->first(); if ($existing) { return; // Already processed, skip re-sending mail }

7. الميزات الناقصة والأخطاء المكتشفة (Missing Features & Issues)

كشف التدقيق الدقيق عن نقطتين حرجتين وملاحظتين متوسطتي الخطورة تؤثران على تشغيل المتطلب بالكامل في الإنتاج:

الخطأ الحرج 1: غياب حزمة Pusher PHP Server SDK في الباك إند

الوصف الفني: يستخدم النظام حزمة laravel/reverb كمخدم ويب سوكت، ولكن في معمارية لارافيل، مشغل البث (Broadcast Driver) الخاص بـ Reverb في كود PHP الداخلي يعتمد بشكل مباشر على مكتبة pusher/pusher-php-server للتواصل مع سيرفر Reverb عبر المنفذ 8080 (بروتوكول Pusher).

الدليل من فحص الكود: ملف backend/my-project/composer.json يحتوي على "laravel/reverb": "^1.6" فقط، ولا يحتوي على حزمة pusher/pusher-php-server.

الأثر العملي: عند إطلاق أي حدث بث مثل OrderCreated أو OrderStatusUpdated عبر مشغل reverb، يتوقف التنفيذ فوراً بالخطأ:

RuntimeException: Failed to create broadcaster for connection "reverb" with error: Class "Pusher\Pusher" not found.

الحل المطلوب: إضافة الحزمة في الباك إند عبر تنفيذ: composer require pusher/pusher-php-server

الملاحظة الحرجة 2: عدم تهيئة مزود بريد حقيقي (Mock Delivery Active)

الوصف الفني: على الرغم من أن فئة MailDeliveryConfiguration تحتوي على شروط صارمة لفحص جاهزية خادم SMTP أو Resend، إلا أن الإعدادات الافتراضية في .env و docker-compose.yml تضبط:

MAIL_MAILER=log ORDER_EMAIL_ALLOW_MOCK=true

الأثر العملي: لا يتم إرسال أي بريد إلكتروني فعلي للعملاء عبر شبكة الإنترنت، بل يتم تسجيل رسائل البريد داخل ملف سجلات لارافيل (Log Driver)، مما يجعل الاختبار T05 غير مكتمل في البيئة الحقيقية.

الملاحظة 3: اعتماد طابور البث على قاعدة البيانات (Database Queue Driver)

في docker-compose.yml:123-140، يعمل broadcast-worker بأمر: php artisan queue:work database --queue=broadcasts استخدام قاعدة بيانات MySQL كوسيط لطوابير البث تحت الضغط العالي ومئات الطلبات المتزامنة يسبب زيادة في استعلامات القفل SELECT ... FOR UPDATE على جدول jobs، وكان من الأفضل توجيهه عبر RabbitMQ أو Redis لزيادة سعة التمرير.

الملاحظة 4: غياب نظام إشراف خارجي (Process Supervisor) داخل الحاويات

حاويات outbox-publisher و email-worker تشغل أوامر Artisan مباشرة كأمر رئيسي (PID 1). في حال حدوث تسريب في الذاكرة (Memory Leak) أو توقف غير متوقع لعملية PHP دون إعادة تشغيل الحاوية من دوكر، قد تتوقف معالجة الطوابير مؤقتاً.

للوصول بالمتطلب الرابع إلى نسبة اكتمال 100% وجاهزية تامة للإنتاج، نوصي باتباع الخطوات التالية مصنفة حسب الأولوية:

9. التقييم النهائي (Final Verdict)

إجابات دقيقة وموثقة بالأدلة الهندسية على الأسئلة الجوهرية لتقييم المتطلب الرابع:

1. هل المتطلب الرابع منفذ ويعمل فعلياً؟

نعم، بنسبة تزيد عن 85% معمارياً وبرمجياً: تم تنفيذ المنظومة بدقة هندسية عالية جداً تفوق الممارسات الشائعة. تم بناء نمط Transactional Outbox، طوابير Quorum في RabbitMQ، آليات إعادة المحاولة المتدرجة، عزل رسائل DLQ، وقنوات الويب سوكت الخاصة مع تحكم أمني محكم. النواقص الحالية تنحصر في حزمة PHP تكميلية واحدة لـ Reverb، وإدخال بيانات مزود بريد خارجي فعلي.

2. هل النظام جاهز للإنتاج (Production-Ready) في وضعه الحالي؟

غير جاهز للإنتاج فوراً (Not Production-Ready Yet): على الرغم من صلابة المعمارية، إلا أن إطلاق النظام في الإنتاج حالياً سيؤدي إلى فشل ميزة التحديث الفوري للأدمن والعميل بسبب غياب حزمة Pusher، كما لن يستلم العملاء أي بريد إلكتروني حقيقي على خوادمهم. بعد تطبيق الخطوتين (الحرجة والعالية) يصبح النظام جاهزاً للإنتاج بكفاءة ممتازة.

3. ما أكبر المخاطر التي تهدد استقرار النظام حالياً؟

أكبر خطر برمجي هو استدعاء أحداث البث التلقائي مما يولد استثناءات RuntimeException في حال عدم التقاطها. وخطر تشغيلي يتمثل في امتلاء طابور DLQ أو جدول Outbox في حال غياب أجهزة المراقبة والتنبيه المبكر عند تراكم الرسائل.

4. هل المعمارية الحالية قابلة للتوسع (Scalable)؟

نعم، قابلة للتوسع بدرجة امتياز: إن فصل مهام النشر عن الـ API عبر Transactional Outbox واستخدام RabbitMQ يسمح بزيادة عدد عمال المعالجة (Workers Horizontally) إلى عشرات النسخ دون أي تغيير في كود التطبيق، كما أن استخدام Laravel Reverb يدعم آلاف الاتصالات المتزامنة بكفاءة ذاكرة منخفضة مقارنة بالحلول التقليدية.

5. ما الخطوات اللازمة لجعل النظام مكتملاً وجاهزاً بنسبة 100%؟
  1. تشغيل أمر: composer require pusher/pusher-php-server داخل backend/my-project.
  2. توفير بيانات حساب SMTP أو Resend في ملف .env وضبط ORDER_EMAIL_ALLOW_MOCK=false.
