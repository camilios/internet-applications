01 · ما المقصود بـ«قبل وبعد» في هذا العرض؟

المشروع الحالي يحتوي الفهارس وRedis والكاش وبقية التحسينات. تشغيل k6 عليه الآن يقيس الحالة الحالية بعد التحسين. قياسات «قبل» الأصلية محفوظة من تشغيلات سابقة قبل التحسينات، وليست أرقامًا مفترضة.

لا تقل إنك شغّلت النسخة القديمة الآن. أمر المقابلة سيعرض ثلاثة عناوين واضحة: ARCHIVED BEFORE وARCHIVED AFTER وLIVE CURRENT (AFTER). الأولان أدلة سابقة، والثالث نتيجة حية وقت العرض.
قل للدكتور:

«قست قبل التعديلات وبعدها على البيانات نفسها وبنفس إعداد k6. هذه ملفات التشغيل الأصلية. سأشغّل الآن النسخة المحسّنة أمامك، وأقارن النتيجة الجديدة بالأدلة المحفوظة، مع توضيح أن ظروف اللابتوب قد تختلف.»

إذا طلب الدكتور تشغيل النسخة القديمة والجديدة كلتيهما مباشرة، تحتاج بيئتين معزولتين ونسخة قاعدة متطابقة قبل الفهارس. ذلك لم يُجهّز في هذا العرض. تعطيل Redis أو مسح الكاش لا يعيد جميع التحسينات، وعمل git checkout وحده لا يزيل الفهارس. لا تغيّر قاعدة المشروع أو تتراجع عن migrations أثناء المقابلة.

04 · اقرأ شاشة k6 بطريقة صحيحة

المصطلحالتفسير الذي تقولهما تنتبه له
endpoint_durationمدة طلب نقطة النهاية فقط؛ نقيسها من response.timings.duration.هذا هو أساس جداولنا. تسجيل الدخول في setup لا يدخل هذا المقياس المخصص.
p50 / p95 / p9950٪ / 95٪ / 99٪ من مدد العينات لا تتجاوز القيمة تقريبًا. الوحدة ms.p95 يوضح الطرف البطيء للتوزيع، وليس المتوسط. الأقل أسرع عند ثبات الحمل والأخطاء.
endpoint_errorsنسبة الاستجابات التي ليست 200 أو 304 في سيناريوهات القراءة هذه.قيمة 0٪ تعني عدم رصد هذا النوع من الأخطاء في التشغيل. السكربت يرفض المقارنة إذا وجد أخطاء في أي تشغيل.
http_reqs / req/sعدد طلبات HTTP ومعدلها في الثانية.يتضمن تسجيل الدخول. وجود sleep وثبات عدد VUs يجعل RPS محدودًا؛ لا أقدمه كسعة النظام القصوى.
data_receivedإجمالي البيانات المستقبلة أثناء التشغيل.يُفيد في شرح ETag، لكن مقدارَه يتأثر بعدد الطلبات والردود؛ ليس حجم JSON واحد.
checksتحققنا من حالة HTTP المتوقعة.نجاحه لا يثبت كل صحة العمل التجاري. لدينا اختبارات مستقلة لصحة الطلبات والمخزون.
thresholdsأهداف يمكن أن تجعل الاختبار يفشل عند تجاوزها.تشغيل المقارنة هنا يستخدم --no-thresholds مثل القياسات السابقة؛ نجاح خروج k6 ليس دليلًا على اجتياز أهداف الأداء.

http_req_duration يشمل إرسال الطلب وانتظار الاستجابة واستقبالها، ولا يشمل DNS وبدء الاتصال. iteration_duration يتضمن sleep؛ لذلك لا تخلطه مع مدة طلب API. حدود الأداء المعرّفة في المصدر موجودة، لكنها غير مطبقة كبوابة نجاح في تشغيلنا هذا.

06 · اربط كل نتيجة بالكود الذي تغيّر

التغييرقبلبعدالشرح أمام الدكتور
فهارس MySQLبعض قوائم الطلبات تفحص عددًا كبيرًا من الصفوف وتفرزها.فهارس user/date وstatus/date وcreated_at، وفهارس للمنتجات.تساعد التصفية والترتيب؛ اختيار الفهرس يعود للمحسن. جدول المنتجات صغير وقد يختار مسحًا.
استعلام الداشبورداستعلامات count/sum منفصلة للطلبات في كل طلب HTTP.تجميع COUNT وSUM وCASE، مع شرط العميل.قلّلنا تكرار العمل مع حفظ نفس مفاتيح JSON ونوع المبيعات العشري.
كاش الداشبوردحساب الأرقام عند كل قراءة.Cache::remember لمدة 60 ثانية؛ مفتاح لكل عميل ومفتاح للمدير.القراءة الدافئة تعيد نتيجة سابقة؛ الكتابة تبطلها فورًا للعميل المعني والمدير.
Redisمخزن الكاش السابق database.خدمة Redis مشتركة للخادم والمجدول وعميل phpredis.قلّلنا الاعتماد على قاعدة البيانات لقراءة الكاش؛ Redis يستهلك ذاكرة وله حدود وسياسة إخلاء.
بيانات المنتجتحميل التصنيف عند كل قراءة.لقطة 300 ثانية نعيد منها علاقة التصنيف فقط؛ stock مستبعد.السعر والظهور من قاعدة التطبيق والمخزون حي عبر gRPC؛ لا نعرض مخزونًا قديمًا لتجميل الأداء.
ETagإرسال JSON كاملًا كل مرة.هاش للاستجابة النهائية و304 عند عدم التغيير.يقلل النقل أساسًا؛ لا يلغي استدعاء المخزون. قياسنا لم يثبت تقليل زمن details في هذه الخطوة.
ثبات الصفحاتترتيب created_at وحده يلتبس عند تساويه.created_at ثم id تنازليًا.تغيير صحة وترتيب، مع الحفاظ على إجماليات pagination.
الإشعار والواجهةالإشعار داخل معاملة الإنشاء، ومفاتيح جديدة عند إعادة المحاولة، ونقص تحديث الاستعلامات.الإشعار بعد commit مع logging؛ مفتاح ثابت لنفس المحاولة وإبطال استعلامات الواجهة.هذه صحة عمل وتقليل زمن داخل المعاملة، وليست السبب المباشر لتحسن GET dashboard في k6.

<?php

namespace App\Http\Controllers;

use App\Models\Order;
use App\Models\Product;
use App\Models\User;
use Illuminate\Http\JsonResponse;
use Illuminate\Support\Facades\Auth;

class DashboardController extends Controller
{
    public function __invoke(): JsonResponse
    {
        $user = Auth::guard('api')->user();
        $orders = Order::query();

        if ($user->role !== 'admin') {
            $orders->where('user_id', $user->id);
        }

        return response()->json([
            'data' => [
                'total_products' => Product::query()->where('is_active', true)->count(),
                'orders_today' => (clone $orders)->whereDate('created_at', today())->count(),
                'total_orders' => (clone $orders)->count(),
                'total_users' => $user->role === 'admin' ? User::query()->count() : null,
                'total_sales' => number_format(
                    (float) (clone $orders)->where('status', '!=', 'cancelled')->sum('total'),
                    2,
                    '.',
                    ''
                ),
            ],
        ]);
    }
}
كود DashboardController بعد التحسين — النسخة الحالية
PHP · النسخة الحالية
<?php

namespace App\Http\Controllers;

use App\Models\Product;
use App\Models\User;
use App\Services\DashboardCache;
use Illuminate\Http\JsonResponse;
use Illuminate\Support\Facades\Auth;
use Illuminate\Support\Facades\Cache;
use Illuminate\Support\Facades\DB;

class DashboardController extends Controller
{
    /**
     * Dashboard numbers may be up to this many seconds old.
     * Services that change orders should call DashboardCache::forgetCache() so the
     * affected user sees fresh numbers immediately.
     */
    private const CACHE_TTL_SECONDS = 60;

    public function __invoke(): JsonResponse
    {
        $user = Auth::guard('api')->user();
        $isAdmin = $user->role === 'admin';

        $data = Cache::remember(
            DashboardCache::cacheKey($user->id, $isAdmin),
            self::CACHE_TTL_SECONDS,
            fn () => $this->buildStats($user->id, $isAdmin)
        );

        return response()->json(['data' => $data]);
    }

    private function buildStats(int $userId, bool $isAdmin): array
    {
        // One pass over the orders table instead of three separate queries.
        // created_at is compared as a range, not with whereDate(), so an index can still be used.
        $orders = DB::table('orders');
        if (! $isAdmin) {
            $orders->where('user_id', $userId);
        }

        $orderStats = $orders->selectRaw(
            'COUNT(*) AS total_orders,
             COALESCE(SUM(CASE WHEN created_at >= ? THEN 1 ELSE 0 END), 0) AS orders_today,
             COALESCE(SUM(CASE WHEN status <> ? THEN total ELSE 0 END), 0) AS total_sales',
            [now()->startOfDay(), 'cancelled']
        )->first();

        return [
            'total_products' => Product::query()->where('is_active', true)->count(),
            'orders_today' => (int) $orderStats->orders_today,
            'total_orders' => (int) $orderStats->total_orders,
            'total_users' => $isAdmin ? User::query()->count() : null,
            // bcmath keeps money as a decimal string, consistent with OrderService.
            'total_sales' => bcadd((string) $orderStats->total_sales, '0', 2),
        ];
    }
}

09 · أسئلة متوقعة وإجابات قصيرة

لماذا ثلاث مرات؟ ولماذا p95 بدل المتوسط فقط؟

لأن تشغيلًا واحدًا يتأثر بتذبذب الجهاز. نعرض الوسيط عبر ثلاث تشغيلات، وp95 يوضح الطلبات الأبطأ التي يخفيها المتوسط. لا تكفي ثلاث تجارب قصيرة لإثبات دلالة إحصائية أو سعة إنتاجية.

هل كنت تختبر كاش دافئًا أم باردًا؟

هذا الحمل يكرر القراءة ولا يمسح Redis بين التشغيلات. قد يحتوي أول تشغيل على misses، ثم يصبح الكاش دافئًا. النتائج تصف هذا المزيج وغلبة القراءات الدافئة، وليست قياسًا معزولًا لـcold start. لا نستخدم cache:clear لتمثيل جميع التحسينات السابقة.

هل 5 VUs تعني 5 طلبات في الثانية أو 5 أنوية؟

لا. VU مستخدم افتراضي ينفذ حلقة طلب وانتظار. معدل الطلبات ينتج عن عدد VUs والزمن وsleep. هذا سكربت يستخدم طلبات HTTP متزامنة لكل VU، وليس نموذج معدل وصول ثابتًا.

لماذا لا نرفع الحمل كثيرًا أمام الدكتور؟

للحفاظ على المقارنة مع الحمل المقاس على هذا اللابتوب. تغيير VUs أو المدة يجعلها تجربة أخرى، ويمكن أن يختبر حدود المعدل أو خادم التطوير بدل أثر التحسين نفسه. العناوين المحاكية توزع VUs كما في الأصل دون تغيير middleware.

كيف نعرف أن السرعة لم تأتِ من بيانات ناقصة أو أخطاء؟

المشغل يحفظ counts ويطبع نسبة endpoint_errors ويرفض المقارنة عند رصد أخطاء. نراجع كذلك الملفات والاختبارات. نفس الأعداد وحدها لا تثبت تطابق محتوى القاعدتين؛ للحالة التاريخية احتفظنا بالبيانات نفسها أثناء جميع مراحل القياس.

هل الكاش يجعل النتائج خاطئة؟

قديمة مؤقتًا ضمن TTL، لذلك فصلنا مفاتيح العملاء وأبطلناها عند الكتابة. لا نخزن stock. TTL الداشبورد 60 ثانية، والتصنيف 300 ثانية. هذه مقايضة موثقة، وليست اتساقًا لحظيًا لكل عميل في كل حقل.

لماذا ليس هناك read replica أو nginx؟

راجعنا القياسات ثم اخترنا تأجيل replica وتقليل خدمات اللابتوب، والإبقاء على خادم التطوير وإجماليات الصفحات. هذه قرارات النطاق الحالي، ولا تعني أن artisan serve مناسب للإنتاج.

ماذا لو كانت النتيجة الحية أبطأ؟

أعرض النتيجة كما هي. أفحص الأخطاء والحمل الآخر وحالة الخدمات ودفء الكاش واختلاف البيانات. لا أكرر حتى أحصل على الرقم الذي يعجبني ولا أسمّي ملفًا من النسخة المحسنة «قبل».

هل k6 يثبت أن واجهة المستخدم صحيحة؟

لا. هذا السكربت يختبر HTTP وحالة الاستجابة، وليس رسم React أو مسار المتصفح الكامل. لدينا اختبارات PHP وMySQL ومكوّنات وAPI مستقلة؛ اختبار Brave الكامل لم ينفذ بسبب منع التحكم عن بُعد.

import http from 'k6/http';
import { check, sleep } from 'k6';
import { randomSeed } from 'k6';
import { Trend, Rate, Counter } from 'k6/metrics';

export const options = {
  scenarios: {
    fixed: {
      executor: 'ramping-vus', startVUs: 0,
      stages: [{ duration: '5s', target: 5 }, { duration: '20s', target: 5 }, { duration: '5s', target: 0 }],
      gracefulRampDown: '1s', gracefulStop: '2s',
    },
  },
  summaryTrendStats: ['p(50)', 'p(95)', 'p(99)'],
  // The runner passes --no-thresholds: these targets are informational, never deployment gates.
  thresholds: { endpoint_duration: ['p(95)<500'], endpoint_errors: ['rate<0.01'] },
};

const duration = new Trend('endpoint_duration', true);
const errors = new Rate('endpoint_errors');
const conditionalHits = new Counter('conditional_hits');
const etags = {};
const base = __ENV.BASE_URL || 'http://ecommerce-backend:8000/api';
let initialized = false;

function headers(token) {
  const result = {
    Accept: 'application/json',
    // Simulate separate clients without disabling or changing the application's rate limits.
    // RUN_ID is deterministic and each VU stays below 60 requests/minute.
    'X-Forwarded-For': `198.18.${__ENV.RUN_ID || 0}.${__VU || 250}`,
  };
  if (token) result.Authorization = `Bearer ${token}`;
  return result;
}

export function setup() {
  const result = http.post(`${base}/login`, JSON.stringify({
    email: 'bulk-customer-1@example.test', password: 'password123',
  }), { headers: { ...headers(), 'Content-Type': 'application/json' } });
  if (result.status !== 200) throw new Error(`Setup login failed: HTTP ${result.status}`);
  return { token: result.json('access_token') };
}

export function request(scenario, auth) {
  if (!initialized) { randomSeed(12345 + __VU); initialized = true; }
  let path;
  if (scenario === 'products-list') {
    const page = 1 + Math.floor(Math.random() * 20);
    const category = 1 + Math.floor(Math.random() * 5);
    path = `/products?page=${page}&category_id=${category}`;
  } else if (scenario === 'product-detail') {
    path = `/products/${1 + Math.floor(Math.random() * 15)}`;
  } else if (scenario === 'customer-orders') {
    path = '/orders';
  } else {
    path = '/dashboard';
  }
  const requestHeaders = headers(auth?.token);
  if (etags[path]) requestHeaders['If-None-Match'] = etags[path];
  const response = http.get(base + path, { headers: requestHeaders, tags: { endpoint: scenario } });
  if (response.headers.Etag) etags[path] = response.headers.Etag;
  conditionalHits.add(response.status === 304 ? 1 : 0);
  duration.add(response.timings.duration);
  errors.add(response.status !== 200 && response.status !== 304);
  check(response, { 'HTTP 200 or valid revalidation': r => r.status === 200 || r.status === 304 });
  sleep(1);
}

"""Compare archived three-run k6 evidence with an optional fresh interview run."""
import argparse
import json
from pathlib import Path
from statistics import median

ROOT = Path(__file__).resolve().parents[1]
SCENARIOS = ('dashboard', 'products-list', 'product-detail', 'customer-orders')
LAST = {'dashboard': 'after-refactor', 'products-list': 'after-refactor',
        'product-detail': 'after-etag', 'customer-orders': 'after-pagination'}

def measurements(folder, scenario):
    paths = [folder / f'k6-{scenario}-{run}.json' for run in range(1, 4)]
    records = []
    for path in paths:
        metrics = json.loads(path.read_text(encoding='utf-8-sig'))['metrics']
        duration = metrics['endpoint_duration']
        records.append({key: float(duration[key]) for key in ('p(50)', 'p(95)', 'p(99)')} | {
            'rps': float(metrics['http_reqs']['rate']),
            'error_percent': 100 * float(metrics['endpoint_errors']['value']),
            'received_bytes': float(metrics['data_received']['count']),
        })
    return records

def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument('--scenario', choices=SCENARIOS, default='dashboard')
    parser.add_argument('--live-dir', type=Path)
    args = parser.parse_args()
    evidence = ROOT / 'docs/performance'
    stages = [('ARCHIVED BEFORE', evidence / 'baseline'),
              ('ARCHIVED AFTER', evidence / 'results' / LAST[args.scenario])]
    if args.live_dir:
        stages.append(('LIVE CURRENT (AFTER)', args.live_dir.resolve()))
    print(f'\nScenario: {args.scenario} | milliseconds | median of THREE run-level percentiles')
    print('Historical after stage:', LAST[args.scenario])
    print('Archived BEFORE is saved evidence, NOT a fresh run of the old application.\n')
    aggregate = {}
    invalid = False
    for label, folder in stages:
        values = measurements(folder, args.scenario)
        print(label, '\n  source:', folder)
        print('  run    p50_ms    p95_ms    p99_ms    req/s   error%')
        for index, row in enumerate(values, 1):
            print(f"  {index:>3} {row['p(50)']:>9.3f} {row['p(95)']:>9.3f} {row['p(99)']:>9.3f} {row['rps']:>8.3f} {row['error_percent']:>8.3f}")
        summary = {key: median(row[key] for row in values) for key in values[0]}
        aggregate[label] = summary
        print(f"  MED {summary['p(50)']:>9.3f} {summary['p(95)']:>9.3f} {summary['p(99)']:>9.3f} {summary['rps']:>8.3f} {summary['error_percent']:>8.3f}")
        print(f"  median received bytes: {summary['received_bytes']:.0f}\n")
        invalid |= any(row['error_percent'] > 0 for row in values)
    if invalid:
        print('INVALID COMPARISON: endpoint errors occurred. Diagnose errors before claiming improvement.')
        return 2
    previous = aggregate['ARCHIVED BEFORE']['p(95)']
    archived = aggregate['ARCHIVED AFTER']['p(95)']
    if previous:
        print(f'Historical p95 reduction: {(previous - archived) / previous * 100:.2f}% (derived from saved runs).')
    if args.live_dir:
        print('Live current timings are new observations; they need not equal historical AFTER.')
        dataset_path = args.live_dir / 'dataset-counts.json'
        if dataset_path.exists():
            dataset = json.loads(dataset_path.read_text())
            expected = {'users': 5004, 'products': 15, 'orders': 300004, 'order_items': 749372}
            print('Current dataset:', dataset)
            if dataset != expected:
                print('DATASET DIFFERENT from recorded baseline. Do not claim a controlled before/after comparison.')
    print('This paced laptop workload is not a maximum-capacity test. No deployment threshold gate was used.')
    return 0

if __name__ == '__main__':
    raise SystemExit(main())
