لنتتبع طلباً واحداً من لحظة ضغط الزبون على زر الشراء. في المتحكم أشير إلى استدعاء خدمة الطلبات، ثم إلى الرد في أسفل الدالة. بين الموضعين تنتظر الصفحة نتيجة إنشاء الطلب فعلاً؛ لا نرجع نجاحاً قبل التحقق من العناصر والمخزون وتثبيت الطلب. الذي أخرجناه من وقت انتظار الزبون هو الاتصال بوسيط الرسائل وما سيحدث بعده. لذلك لا أبحث في هذا المتحكم عن أمر يرسل بريداً أو ينتظر موافقة RabbitMQ.

عندما ترجع الخدمة بنجاح نحول الطلب إلى استجابة تحمل 201 ورقمه. معنى هذه الإجابة محدد: أصبح لدى الزبون طلب محفوظ. قد يكون البريد قيد الانتظار في هذه اللحظة، وهذا طبيعي. والسؤال الذي يأخذني إلى الملف التالي هو: إذا أغلق الزبون الصفحة فور ظهور الرقم، أين حفظنا المعلومة التي ستدفع النظام إلى نشر الحدث؟

في مثال طلبنا، يمكن أن يصل الرد للمتصفح بينما حدثه لم يغادر MySQL بعد. لا توجد منافسة مطلوبة بين سرعة المتصفح وسرعة الناشر؛ حتى لو سبق الناشر الرد مرة، لا تعتمد صحة الرد على ذلك السباق.

داخل createOrder أذهب مباشرة إلى المعاملة المميزة. تخيّل حلّاً يحفظ الطلب أولاً، ثم يحاول النشر من الذاكرة: لو تعطلت العملية بين الخطوتين، سيجد الزبون طلبه في حسابه لكن لا يبقى شيء يخبر الناشر بأن لهذا الطلب حدثاً. هنا وضعنا إنشاء سجل الطلب وكتابة سجل الحدث في المعاملة نفسها. فإذا تراجعت المعاملة لا يبقى حدث لطلب لم يكتمل، وإذا نجحت يبقى سجل يمكن لعملية أخرى قراءته حتى بعد انتهاء عملية HTTP.

أنظر إلى الحمولة بصفتها وصفاً لواقعة واحدة: رقم الطلب يحدد أيّ طلب نعنيه، ومعرّف الحدث يميّز واقعة الإنشاء، والوقت يبيّن متى حصلت. نعيّن وقت الإتاحة الآن؛ هذا يجعل الحدث مستحقاً للنشر، ولا يعني أن الوسيط استلمه. وإذا كانت عملية الشراء قد اكتملت سابقاً، فالمسار الذي يسترجع الطلب الموجود لا ينشئ له حدثاً جديداً في كل إعادة محاولة. لهذا أميّز بين مفتاح محاولة الشراء ومعرّف رسالة النشر.

في الجدول نفسه يربط رقم الطلب سجل الحدث بسجل الشراء. لو كنا نتحقق من طلب واحد بعد عودة الخدمة لاستطعنا تتبع واقعة الشراء بهذا الرقم، ثم تتبع محاولات نشر الواقعة بمعرّفها الثابت.

    public function handle(OutboxPublisher $publisher, MessageBroker $broker): int
    {
        DB::connection()->useWriteConnectionWhenReading();
        do {
            try {
                $worked = $publisher->publishNext();
            } catch (\Throwable $exception) {
                $broker->close();
                Log::error('Outbox publisher recovering', ['error_type' => $exception::class]);
                if ($this->option('once')) {
                    return self::FAILURE;
                }
                sleep(config('rabbitmq.reconnect_delay'));

                continue;
            }
            if (! $this->option('once') && ! $worked) {
                sleep(config('rabbitmq.poll_interval'));
            }
        } while (! $this->option('once'));
        $broker->close();

        return self::SUCCESS;
    }

الآن صار الطلب محفوظاً وخرج الزبون من المسار. في Compose أفتح تعريف خدمة الناشر وأشير إلى أمر التشغيل. نفس مشروع Laravel له هنا عملية أخرى مستقلة عن خادم الويب: خادم الويب يستقبل الشراء، وهذه الحاوية تشغّل أمر نشر الأحداث. لو أوقفنا الناشر بعد حفظ الطلب، لا نحتاج من الزبون أن يعيد شراء السلة. السجل باقٍ في قاعدة البيانات ويمكن للناشر اكتشافه عندما يعود.

داخل أمر Artisan نقرأ من الاتصال الرئيسي ونطلب معالجة حدث واحد في كل دورة. اختيار الاتصال مهم لحدث كُتب للتو، حتى لا تقرر العملية خطأً أن لا عمل لديها بسبب تأخر نسخة القراءة. إذا وجدت عملاً تنتقل للدورة التالية، وإذا لم تجده تنتظر قليلاً قبل السؤال من جديد. هذا الانتظار يخص عملية الناشر؛ لا يوجد متصفح فاتح اتصال شراء ينتظر انتهاء هذه الحلقة.

وهذا يفسر لماذا لدينا عمليتان خلفيتان مختلفتان. إذا أردت معرفة لماذا لم يصل الحدث إلى الوسيط أبدأ من الناشر. أما إذا كان الحدث منشوراً والبريد متأخراً فموضع الفحص التالي هو المستهلك.

    public function publishNext(): bool
    {
        return DB::transaction(function (): bool {
            $event = OutboxEvent::query()->useWritePdo()
                ->whereNull('published_at')->where('available_at', '<=', now())
                ->orderBy('available_at')->orderBy('event_id')->lockForUpdate()->first();
            if ($event === null) {
                return false;
            }

            try {
                $this->broker->publish(
                    json_encode($event->payload, JSON_THROW_ON_ERROR),
                    $event->event_id,
                    config('rabbitmq.exchange'),
                    config('rabbitmq.routing_key'),
                );
            } catch (\Throwable $exception) {
                $attempts = $event->attempts + 1;
                $event->update([
                    'attempts' => $attempts,
                    'available_at' => now()->addSeconds(min(config('rabbitmq.publisher_max_backoff'), 2 ** min($attempts, 12))),
                    'last_error' => $exception::class,
                ]);
                $this->broker->close();
                Log::warning('Outbox publication deferred', ['event_id' => $event->event_id, 'attempt' => $attempts, 'error_type' => $exception::class]);

                return true;
            }

            // A crash after the confirm but before this commit republishes the same event ID.
            $event->update(['published_at' => now(), 'attempts' => $event->attempts + 1, 'last_error' => null]);
            Log::info('Outbox publication confirmed', ['event_id' => $event->event_id]);

            return true;
        }, 1);
    }

ما تقوله

في publishNext لا نختار أي صف من الجدول. نريد حدثاً لم يحصل على تاريخ نشر، وقد حان موعده. نرتب النتائج ونقفل صفاً واحداً داخل معاملة حتى لا تتعامل عمليتان مع السجل نفسه على أنهما أول من اختاره. بعد ذلك تتحول الحمولة المحفوظة إلى JSON، ويُمرَّر معها معرّف الحدث واسم الموزّع ومفتاح التوجيه. الموزّع يستقبل الرسالة، والمفتاح يحدد أي ربط بالطوابير يطابقها.

قبل الانتقال إلى تنفيذ النشر، أشير إلى نهايتي الدالة. عند الفشل نحفظ عدد المحاولات وموعداً لاحقاً يتباعد إلى حد مضبوط، ويظل تاريخ النشر فارغاً. أما تعيين تاريخ النشر فيقع في مسار النجاح فقط. لو انعكس الترتيب وسجّلنا النجاح قبل الاتصال بالوسيط، فقد يختفي الحدث من قائمة الانتظار مع أنه لم يغادر قاعدة البيانات. الذي يحدد أي المسارين نتخذ ليس نجاح حفظ الطلب، بل نتيجة عملية النشر التالية.

مثلاً إذا انقطع الاتصال عشر ثوانٍ، لا نعلن فشل عملية الشراء التي انتهت أصلاً. ما أخفق هو محاولة إرسال الحدث. نجعل وقت الإتاحة في المستقبل ثم نعود للأحداث المستحقة الأخرى.

    public function publish(string $body, string $eventId, string $exchange, string $routingKey, int $attempt = 1): void
    {
        $channel = $this->channel();
        $confirmed = false;
        $failed = false;
        $channel->set_ack_handler(function () use (&$confirmed): void {
            $confirmed = true;
        });
        $channel->set_nack_handler(function () use (&$failed): void {
            $failed = true;
        });
        $channel->set_return_listener(function () use (&$failed): void {
            $failed = true;
        });
        $message = new AMQPMessage($body, [
            'content_type' => 'application/json',
            'delivery_mode' => AMQPMessage::DELIVERY_MODE_PERSISTENT,
            'message_id' => $eventId,
            'type' => 'OrderCreated',
            'timestamp' => time(),
            'application_headers' => new AMQPTable(['attempt' => $attempt]),
        ]);
        $channel->basic_publish($message, $exchange, $routingKey, true);
        $channel->wait_for_pending_acks_returns(config('rabbitmq.confirm_timeout'));
        if (! $confirmed || $failed) {
            throw new RuntimeException('RabbitMQ did not confirm a routed message.');
        }
    }

ما تقوله

هذا موضع النشر الفعلي في RabbitMQ. نجهز الرسالة بمعرّف الحدث ذاته ونختار لها وضع الحفظ الدائم. الدوام خاصية للرسالة أيضاً، وليس مجرد تسمية للطابور. في basic_publish الوسيط الأخير true يعني mandatory: إذا لم يجد الموزّع طريقاً من مفتاح التوجيه إلى طابور مطابق، نريد أن يعرف الناشر أن الرسالة رجعت. الاتصال بالشبكة وحده ليس كافياً لإعلان النجاح.

بعد النشر ننتظر التأكيد أو الإرجاع ضمن مهلة. جواب التأكيد يأتي من RabbitMQ إلى الناشر؛ لا يخبرنا أن الزبون قرأ بريده أو أن العامل أنهى الإرسال. إذا رُفضت الرسالة أو لم يصل التأكيد المطلوب، يرمي الكود استثناءً فيعود التنفيذ إلى مسار التأجيل الذي شرحناه. ولو قبلها الوسيط ثم تعطّل الناشر قبل تسجيل النجاح في قاعدة البيانات، قد يُعاد نشر المعرّف نفسه. النتيجة التي نستطيع الدفاع عنها هي أن الحدث لا يُنسى بين إنشاء الطلب والنشر، لا أن الشبكة تضمن وصوله مرة واحدة فقط.

إذا سُئلت أين انتهى النشر بالنسبة للتطبيق، أشير إلى موضعين لا موضع واحد: قبول رسالة موجّهة هنا، ثم تثبيت تاريخ نشرها في السجل السابق. أما تسليم رسالة البريد للمزوّد فقصة تالية.
