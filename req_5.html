def docker(*args, input=None, check=True):
    raw = subprocess.run(['wsl.exe', '-d', 'Ubuntu', '--', 'docker', *args],
                         input=input.encode('utf-8') if input is not None else None, capture_output=True)

ج ـ نفهم الأداة من بداية الملف إلى نهايته

السطر أو الجزءالتفسير بالتفصيل
bootstrap Laravel / useWriteConnectionWhenReadingتهيئ Laravel داخل الحاوية، وتفرض قراءة primary لعملياتها المحلية المباشرة. طلبات HTTP التي ترسلها بعد ذلك منفصلة وتسير عبر طبقات API؛ لا تنتقل هذه العلامة تلقائيًا إلى كل طلب شبكي.
checklistHttp(method,path,token,body,headers)دالة واحدة ترسل GET أو PATCH أو غيرها بالـJSON. تضيف Bearer للطلب الإداري، وتحتفظ بالحالة والترويسات وطول الجسم والبيانات المفكوكة. الجسم الفارغ يعاد null حتى لا يسبب304 خطأ json_decode.
ignore_errors / transport exceptionتسمح بقراءة رد HTTP غير200 لتفحصه، لكن فشل النقل يوقف الأداة. واستخراج الترويسات بحروف صغيرة يجعل التحقق من etag ثابت الاسم.
checklistRequireأي شرط كاذب يوقف الأداة باستثناء. لا تُكتب passed:true في المخرجات النهائية إن لم تصل كل الفحوص إلى نهاية المسار الناجح.
ProductCache + Cache::store(redis)نصل إلى خدمة الكاش وإلى مخزن Redis لكي يجمع الدليل بين سلوك HTTP وحالة المفتاح وTTL الحقيقية.
UUID / category / product / probeننشئ أسماء ومفتاح اختبار مميزًا، ونحتفظ بمعرفات البيانات التي تخص التجربة كي يمكن إزالتها في finally. لا تعدل أداة الفحص منتجًا عشوائيًا للعميل.
admin tokenنولد token لمسؤول موجود لإجراء تعديلات التصنيف والمنتج عبر API المحمية. هذا اختبار سير عمل مصادق، لا طلب PATCH عام بلا مصادقة.
GET أول ثم snapshot وTTLيسخن الكاش ويأخذ الوسم، ويؤكد أن stock ليست ضمن النسخة المخزنة، وأن TTL موجبة ولا تتجاوز300 ثانية.
PUT التصنيف ثم cache nullيغير اسم التصنيف، ويثبت إبطال التفاصيل المتأثرة. GET بالوسم القديم يجب أن ترجع200 واسم التصنيف الجديد، ثم قراءة أخرى بالوسم الجديد ترجع304 بلا جسم.
PATCH price=2.50 ثم cache nullهذا قلب الاختبار: يحفظ السعر عبر HTTP ثم يفحص زوال المفتاح. لا يضيف sleep بانتظار انتهاء TTL قبل القراءة.
GET مع If-None-Match السابقيرسل وسمًا سابقًا، ويؤكد200 وقيمة price=2.50. لو رجع304 خاطئة أو السعر القديم فسيفشل الشرط.
dashboard TTL / expiry probeيسخن إحصاءات المسؤول ويفحص TTL حتى60 ثانية، ثم مفتاح probe بعمر ثانية وينتظر1.2 ثانية لإثبات الانتهاء الحقيقي. هذا الانتظار خاص بتجربة expiry بعد فحص السعر، وليس انتظارًا لتحديث السعر.
DELETE ثم null ثم404يتحقق من إبطال المفتاح عند الحذف ومن عدم إعادة بيانات منتج حذفناه.
finally / ownership checkحتى عند الفشل يحاول تنظيف البيانات المملوكة. يسترجع المنتج مع المحذوفة ويطابق اسمه باسم التجربة قبل forceDelete، ويمحو مفتاحه ويحذف التصنيف والـprobe ويبطل ملخص المسؤول.

هذه الأداة تغير fixtures وتعيد تنظيفها؛ ليست قراءة تحميل فقط. لم نشغلها عند إنشاء هذا الدليل. ويجب فصل نتيجتها عن قياس throughput: طلب PATCH ثم GET متتالٍ يثبت السعر الظاهر ولا يثبت أن جميع القراء المتزامنين يشاهدونه في كل توقيت من أي توبولوجيا.

ما معنى «يظهر فورًا» هنا؟

المعنى المثبت: بعد نجاح الكتابة، القراءة الجديدة التي ينفذها الاختبار ترجع السعر الجديد من الـAPI دون انتظار TTL. لا يوجد في هذا الدليل قياس لعدد ميلي ثوانٍ بين كل عملية وأخرى، ولا دفع آلي لتغيير السعر إلى صفحة مفتوحة. ظهوره في واجهة مفتوحة يتطلب قراءة جديدة أو آلية تحديث في العميل؛ هذه مرحلة خارج نطاق فحص backend الحالي.

ما أقوله للأستاذ: «اختبرت السرعة والصحة كلًا بدليله. بعد تعديل المنتج أحذف كاشه، ثم أقرأ بالسعر الجديد من API دون انتظار TTL. Feature test تثبت السلوك بمحاكاة المخزون، وchecklist-cache تثبته في HTTP وRedis الحقيقيتين وفق الدليل المحفوظ. هذا ليس سيناريو PATCH تحت حمل k6 ولا دفعًا تلقائيًا لواجهة مفتوحة.»
قبل الانتقال: أشر إلى PATCH ثم cache-null ثم GET الجديدة في الفاحص. وضح لماذا لا ننتظر300 ثانية، ولماذا sleep في probe لا يعني أن السعر انتظر للتحديث.

أسئلة محتملة وإجابات بسيطة ودقيقة

لماذا اخترت أربع عمليات؟

لأنها مسارات قراءة مختلفة: القائمة، التفاصيل، طلبات المستخدم، والإحصاءات. تختلف الاستعلامات والمصادقة والكاش فيها، لذلك لا تكفي قراءة واحدة للحكم على النظام كله.

هل5VUs تعني5 طلبات في الثانية؟

لا. هي5 مستخدمين افتراضيين يكررون العمل. كل دورة فيها انتظار الرد وثانية تفكير، فيتغير المعدل مع زمن الرد ومراحل الحمل.

لماذا كررت كل اختبار ثلاث مرات؟

لتقليل اعتماد النتيجة على تشغيل واحد ومشاهدة اختلاف التشغيلات. أعرض وسيط قيمها، لكنه لا يلغي أثر البيئة أو يجعل العينة كبيرة تلقائيًا.

ما الفرق بينp50 وp95 وp99؟

الأولى تصف وسط التوزيع، والأخريان تصفان طرفه الأبطأ. نقرأ الثلاث حتى لا نخفي بطء عدد قليل من الطلبات خلف متوسط جيد.

هلp95 في الجدول محسوبة من كل الطلبات المدمجة؟

لا. كل تشغيل لهp95، والجدول يأخذ وسيط القيم الثلاث. هذا مختلف عن دمج العينات الخام ثم حسابp95 واحدة.

لماذا لا أستعملhttp_req_duration فقط؟

لأنها تشمل كلHTTP، ومنهاsetup login. أنشأنا endpoint_duration لطلبات العملية نفسها، كي نقارن زمن القراءة دون تسجيل الدخول وsleep.

أين تظهر تكلفة تسجيل الدخول؟

تدخل ضمنhttp_reqs وعددها ومعدلها، وقد تدخل مقاييسHTTP المدمجة. لكنها لا تدخلTrend الخاصة بقراءات العملية.

كيف عرفت أن الأخطاء صفر؟

راجعت endpoint_errors.value وhttp_req_failed.value وفشل checks في كل تشغيل خام، لا صف الوسيط فقط. هذا يثبت عدم رصد الأخطاء المغطاة في العينة.

هل200 تثبت أن JSON والسعر صحيحان؟

لا في common.js؛ فحصها عام للحالة200 أو304. compression.js تضيف تحققًا جزئيًا من JSON، وأداة التحديث تختبر السعر بعد PATCH تحديدًا.

لماذا لم تفشلk6 عندcheck فاشلة؟

check تسجل النتيجة وتتابع. لجعل معيار ما يحكم نجاح التشغيل نحتاجthreshold مفعلة. المشغلات هنا تمررno-thresholds، لذلك نراجع المقاييس المصدرة أيضًا.

هلbaseline أُعيدت يوم10نوفمبر؟

لا. before-after.json تصرحbaseline_rerun=false. المقارنة تستخدم أدلةbaseline التاريخية مع قياس النسخة المنشورة الحالي.

هل يكفي تغيير اسم الإخراج إلىbaseline.csv؟

لا. اسم الملف لا يبدل التطبيق أو الفهارس أو الكاش. مقارنةقبل وبعد تحتاج تنفيذ المرحلتين فعليًا ببيانات وسياق موثقين.

هل تقدر استخراج كل العينات منp99 وحدها؟

لا. الملخص فقد تفاصيل التوزيع الأصلي. CSV الخام تسجل نقاط مقاييس يمكن تحليلها، ولا نعيد خلقها من ثلاثمئينات.

هل سجلّيت الإصدار أم اكتفيت بوسمlatest؟

الدليل يحفظk6-version.txt في الجهتين ويعرضv2.3.0. وسمlatest وحده قد يشير إلى صورة أخرى في وقت لاحق.

لماذا أذكر قيدًا لحمل القائمة؟

لأنه يختار صفحات1 إلى20 وتصنيفات1 إلى5 من15 منتجًا فقط؛ قد يكثر الرد الفارغ. لذلك لا أقدمه كقياس لجميع الصفحات الممتلئة أو البحث الثقيل.

أين أثرت304 على القياس؟

لا. مثلًاp99 لطلبات العميل ارتفعت مننحو142.562إلى148.358ms. انخفضp50 وp95 لها، لكن لا يصح الادعاء بأن كل الطلبات أسرع.

هل أثبتّ أنRedis وحدها سبب الانخفاض؟

كيف أثبت ظهور السعر الجديد؟

هل اختبرت تعديل المنتج أثناء حمل k6؟

لا في السيناريوهات الحالية. دليل التعديل اختبار صحة متتالٍ منفصل، وليس PATCH تحت حمل متزامن. سأوضح ذلك بدل نسبته إلى k6.

هل تعني فورًا أن صفحة المستخدم المفتوحة تتغير آليًا؟

لا. الدليل يثبت أن القراءة التالية من API حديثة دون انتظار TTL. تحديث صفحة مفتوحة يحتاج قراءة جديدة أو آلية دفع في العميل.
